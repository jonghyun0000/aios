# 실제 로컬 앱 접근성 보완과 검증 범위

검사일: 2026-09-12. 대상은 공개 체험 데모가 아니라 `apps/web`이다.

사용자 흐름은 대화/자료 화면에서 키보드로 작업을 시작하고, API가 반환한 승인·오류·복구 상태를 읽으며, 다음 행동으로 초점을 이어가는 과정이다. 사용자 DB·파일을 바꾸지 않는 합성 API 시험과 실제 운영 서버의 읽기 검사를 구분했다. 아래 결과는 WCAG 인증이나 접근성 100점 판정이 아니다.

## 처음 확인한 문제

| 경계 | 확인한 근거 | 수정 |
| --- | --- | --- |
| 긴 대화 읽기 | 밝은/어두운 화면, 데스크톱/390px 모두 `.messages`에서 `scrollable-region-focusable` 위반 | 이름 있는 대화 영역과 Tab 진입, Home/End 스크롤 |
| 설정의 긴 조직 ID | 390px 설정 표가 가로 스크롤을 만들지만 키보드 진입점 없음 | 표의 열 너비·줄바꿈을 지정하고 가로 스크롤 제거 |
| 설정 조회 장애 | 세션 API의 503도 정상적인 “세션 없음”으로 처리 | 로컬/API 키/JWT의 예상 401·404만 정상 처리; 나머지는 오류와 재시도 |
| 자료·이름 모달 | 첫 회귀에서 Shift+Tab이 모달 밖으로 이동, 이름 입력 초기 초점 실패 | native dialog의 배경 비활성화 유지, Tab 경계 처리, 표시 후 초기 초점과 닫은 뒤 호출 버튼 복귀 |
| 승인 이후 | 마지막 대기 작업이 승인되면 결과가 접히며 초점이 사라질 수 있음 | 승인/거절 후 증거를 펼친 채 유지, 결과 토글로 초점 연결 |
| 긴 변경 비교 | 변경 전후·명령·출력이 스크롤 영역인데 직접 키보드로 읽기 어려움 | 각 영역 이름과 키보드 진입점 제공 |
| 협업 편집 | textarea에 명시 이름이 없고 “로컬 보관”이 영속 저장으로 오해될 수 있음 | 문서별 편집기 이름·도움말 연결; 탭 메모리/연결 단절/새로고침 손실 한계 명시 |
| 좁은 화면 대화 메뉴 | 메뉴를 닫을 때 내부 링크 초점이 숨겨질 수 있음 | Escape 또는 대화 선택 후 메뉴 버튼으로 초점 복귀 |
| 펼친 기억 설명 | 세로 공간이 부족하면 대화 영역 높이가 0으로 축소 | 대화 최소 높이 120px, 채팅 패널 세로 스크롤, 입력란 접근 확인 |
| 높이가 낮은 노트북 창 | 후속 실제 1280×577 화면에서 최근 대화 목록이 사실상 가려짐; 기록 영역 80px, 내부 목록 8px | 높이 700px 이하·너비 761px 이상에서 사이드바 세로 스크롤과 기록 영역 최소 높이 지정. 같은 짧은 창에서 기록 영역 220px, 내부 목록 93px 확인 |

협업 문서 선택도 form으로 바꾸어 문서 이름에서 Enter로 이동한다. 기존 채팅의 Enter 전송·Shift+Enter 줄바꿈·IME 보호는 유지한다.

## 기억·참고자료의 화면 계약

`workspace_context`의 기존 필드와 새 선택 필드를 함께 처리한다. 세부 API 정책은 [기억과 근거](25-context-and-evidence.md)를 참고한다.

- 본문은 **실제 모델에 전달한 과거 메시지 수**를 표시한다. 최근 100개 상한과 입력 예산 때문에 빠질 수 있는 범위를 안내한다.
- 연결·조회한 파일 수와 실제 전달된 자료를 구분한다. `referenceMode=none`이면 연결 파일이 있어도 “답변에 전달된 자료 없음”이라고 표시한다.
- 출처는 실제 전달한 파일 이름·행 범위다. 자료 전체를 검증했거나 답변이 정확하다는 보증이 아님을 함께 표시한다.
- 기억 선호는 한국어/영어, 목록/일반 문장, 간결하게/자세하게만 표시한다. 알 수 없는 enum과 손상된 행 범위는 근거로 표시하지 않는다.
- 사용자 메시지의 실제 검사 수와 최근 최대 500개 상한을 함께 표시한다. 당장의 명시 요청이 우선이다.
- 기억을 끄면 이후 요청에 `context.useMemory=false`를 보낸다. 채팅 저장 중지나 대화 삭제가 아니라는 점을 설명한다.
- “답변 선호 초기화 문장 넣기”는 **빈 입력란**에 `이 대화의 답변 선호를 초기화해줘.`만 넣는다. 자동 전송하지 않는다. 초안이 있으면 버튼을 비활성화해 덮어쓰지 않고, 먼저 전송하거나 별도 보관하라고 안내한다. API는 이 독립 문장을 단독으로 전송했을 때만 초기화하므로 초안 뒤에 덧붙이지 않는다.

React 검토에서는 기존 서버 저장본 재조회와 중단 신호를 유지했다. 사용자 동작에 따른 초점 이동은 해당 이벤트에서 처리하고, 모달 생성/해제만 수명주기 효과로 처리했다. 단순한 표시 문자열은 순수 함수에서 계산하며 별도 저장소나 외부 UI 라이브러리를 추가하지 않았다.

## 실행한 검사

### 실제 운영 서버 읽기

초기 읽기 검사에서는 `127.0.0.1:8791/readyz`에서 Postgres/Redis 정상 응답을 확인했다. agent-browser 전용 세션으로 새 빈 채팅과 설정을 열어 로그인 없이 로컬 owner 화면이 렌더되는지 확인했다. 당시 `assets/index-CgPICoUU.js` 로드도 확인했다. 이는 아래 짧은 창 보완 전 산출물의 역사적 기록이다. 이 초기 검사에서는 메시지 전송, 기존 문서 편집, 자료 변경, 승인/복구, 서버 재시작을 하지 않았다.

따라서 이 결과 자체는 새 기억 정책의 모델 품질이나 실제 DB 쓰기 성공을 입증하지 않는다. 운영 API 재기동·실제 쓰기 흐름은 별도 통합 검증의 책임이다.

### 독립 합성 브라우저 시험

`apps/web/a11y.config.ts`는 빌드된 실제 UI를 4175 정적 preview로 띄운다. Playwright `webServer`가 기동과 종료를 관리하고 CI에서는 이미 열린 서버를 재사용하지 않는다. 모든 `/v1/**`와 협업 WebSocket을 가로채므로 API/DB/Redis/Ollama 없이 실행한다. 지정하지 않은 API 요청도 실제 서버로 전달하지 않고 시험 오류로 처리한다.

최신 실행은 짧은 노트북 창 회귀 4개를 추가한 **36 PASS, 0 FAIL**이다. 이전의 **32 PASS, 0 FAIL, 재시도 0회, 20.8초**는 짧은 창 보완 전 실행 기록이며 최신 시험 수로 사용하지 않는다.

| 시험 흐름 | 확인한 내용 |
| --- | --- |
| 긴 대화 | 이름 있는 영역에 Tab 진입, Home으로 처음 읽기, 본문 바로가기 초점 |
| 자료·이름 | 파일 저장 실패와 기존 목록 보존, Tab 경계, Escape 호출 버튼 복귀, 이름 저장 실패 시 초안 보존 |
| 승인·복구 | 승인 503 표시 후 재시도, 긴 변경 내용 End 스크롤, 승인 후 증거 유지, 복구 409와 현재 내용 보존 안내 |
| 설정 | 세션·운영 기록 503을 정상 상태와 구분, 두 재시도 후 정상 안내 |
| 협업 | 문서 이름 Enter, 편집기 이름, 합성 WS 연결/단절, 탭 메모리의 편집 보존과 손실 경고 |
| 기억·출처 | 기억 off 요청 본문, 저장 지속 안내, enum·검사 수·행 범위, 초안 보존, 단독 초기화 문장 |
| 320px 메뉴 | 키보드 열기·Escape 닫기·대화 선택 후 버튼 초점, 가로 넘침 없음 |
| 낮은 노트북 창 | 1280×600에서 대화 목록 높이가 실제 링크 한 줄보다 작지 않은지, 키보드 초점 시 링크 전체 노출과 Enter로 대화 열기 |
| 의도적 결함 | `.messages`의 tabindex를 제거하면 axe가 실제 위반을 검출하고, 복원하면 사라짐 |

최신은 9개 흐름 × 밝은/어두운 테마 × 데스크톱/모바일 프로젝트 = 36개다. 기본 크기는 1280×800/390×844이며, 메뉴 시험은 두 프로젝트에서 모두 너비를 320px로 좁히고 낮은 창 시험은 모두 1280×600으로 바꾼다. 초기 진단에는 1366px, 후속 실제 창 확인에는 1280×577을 사용했다. 자료/승인/복구 등 서버 반응은 합성이므로 실제 파일 변경/복구나 모델 정확성 증거로 세지 않는다.

최신 화면 상태별 axe-core 4.10.3 검사는 **48회, 확정 자동 위반 0개**다. 사용 태그는 `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`, `best-practice`이다. **46/48개 상태에 `color-contrast` 수동 확인 대상이 남고, 대상 출현 수는 합계 358개**다. 이는 중복 출현을 포함한 수로 358개의 고유 결함을 뜻하지 않는다. 장식 기호, placeholder 또는 스크롤 밖 요소 등이 포함되므로 이를 “모든 대비 검사 통과”로 계산하지 않는다. 이전의 44회/위반 0/수동 확인 42상태는 32개 시험 시점의 역사적 수치다.

별도로 CSS의 보조 텍스트/활성 메뉴 색 조합을 계산했다. 보조 텍스트 대비는 밝은 테마 5.33~5.72:1, 어두운 테마 6.49~7.43:1, 활성 메뉴는 각각 6.29:1과 5.22:1이다. 변경 전부터 확보된 대비는 유지했고, 밝은/어두운 모달·오류·320px 메뉴·기억 설명 스크린샷에서 겹침과 잘림을 검토했다. 이 표본 계산이 모든 상태의 대비를 대신하지 않는다.

시험 하네스의 초기 증거 저장에서 `/`가 들어간 라벨을 경로로 처리해 4개 실패한 이력이 있다. 파일명 정규화 후 새 출력 폴더에서 다시 실행해 통과했다. 재시도로 감추지 않았다. 시험 종료 후 4175 리스너가 남지 않음을 확인했고, 전용 agent-browser 세션만 종료했다.

### 타입·단위·정적 검사

- 웹 타입 검사 및 프로덕션 빌드 통과.
- 웹 src 및 신규 접근성 시험/설정에 대한 ESLint 경고 0.
- 웹 단위 시험 **35/35 통과**. 세션 오류 분류 3개, 기억·출처 표시/손상 주입 5개, 기존 시험 27개 포함.
- `git diff --check` 통과.
- 짧은 창 보완 후 재검사 산출물: `index-CDBMODiX.css`, `index-D8yo5yRo.js`.
- 이전 32개 시험 당시 산출물 `index-qIRbNyxO.css`, `index-CgPICoUU.js`는 역사적 기록으로 보존한다.

## 재현

저장소 루트에서 의존성과 Chromium을 준비한 뒤 실행한다.

```sh
pnpm --filter @aios/web build
pnpm --filter @aios/web exec playwright test --config a11y.config.ts
```

CI에서는 `CI=1`을 설정한다. 별도 살아 있는 API는 필요 없다. 결과는 `PLAYWRIGHT_OUTPUT_DIR`로 지정할 수 있으며 출력 폴더는 Playwright가 정리하므로 사용자 자료 폴더를 지정하지 않는다. 최신 36개 시험/48개 axe 보고·스크린샷은 `/Volumes/T7/bigdata/tmp/app-a11y-c0uuT6`에 있다. 해당 폴더의 원본 `*-axe.json`을 중복 첨부/AppleDouble 파일 없이 집계해 위 수치를 확인했고 `.last-run.json`도 `passed`, 실패 목록 0개다. 이전 32개 시험은 `/Volumes/T7/bigdata/tmp/aios-web-a11y-WqRD5I/results-contract-final`, 최초 진단은 같은 상위 폴더의 `baseline.json`에 보존한다. 이 경로는 로컬 증거 위치이며 Git에 포함하지 않는다.

## 남아 있는 검증 한계

- 독립 신규 사용자, 실제 VoiceOver/NVDA, Safari/WebKit, 실제 iPhone 또는 다른 M1 Mac에서의 실사용은 이번 시험에 포함하지 않았다.
- OAuth 계정·다른 조직·마켓플레이스·공공통계·결제의 전체 흐름을 새로 감사한 것은 아니다.
- 합성 WS는 연결 상태/오류 UI 검사이며 실제 다중 참여자 동기화·서버 종료 저장 시험을 대체하지 않는다.
- 자동 검사와 표본 시각 검토가 화면 읽기 순서의 자연스러움, 모든 배율/사용자 설정, 모든 문장 이해 가능성을 보장하지 않는다.
- 다른 M1 Mac에서는 로컬 설치·기동·첫 대화·자료·승인·검증·복구를 직접 실행하고, 키보드만으로 완료 가능한지 다시 확인해야 한다.
