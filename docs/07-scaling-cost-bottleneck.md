# 12. Scaling 전략 & 13. 비용 분석 & 14. 병목 분석

## 12. Scaling 전략

### Phase 1 — ~1k 활성 사용자 (현 코드 그대로)
- api ×2 (LB 뒤), worker ×2, Supabase Pro, Redis 단일(레플리카 1)
- WS는 Redis PubSub 팬아웃이라 api 노드 수평 확장에 이미 대응됨
- 병목 없음: LLM 지연이 지배적이라 우리 인프라는 한가하다

### Phase 2 — ~10k
- **indexer worker 분리 배포**: 임베딩 배치가 CPU/네트워크를 태우므로 api와 자원 격리 (코드는 이미 큐 뒤에 있어 배포 매니페스트 변경만으로 분리됨 — 이것이 modular monolith의 배당금)
- **sandbox 전용 노드 풀**: Docker-in-Docker 제거, 워밍 풀(대기 컨테이너 N개)로 콜드스타트 상쇄
- Postgres: pgbouncer(transaction mode) 필수 — Node 풀 × 노드 수가 커넥션 한도를 초과하는 시점
- 읽기 레플리카: 검색/히스토리 조회 분리

### Phase 3 — 100k+
- usage_events/audit_logs 월별 파티셔닝, 콜드 파티션은 오브젝트 스토리지로
- 벡터: 프로젝트 샤딩(org_id 해시) 또는 Qdrant 이관 — `VectorStore` 인터페이스 뒤라 앱 코드 무변경
- EventBus: Redis Streams → NATS JetStream (컨슈머 수십 개 초과 시)
- 지역 분산: LLM 프록시 PoP만 멀티리전(프로바이더 리전 근접), 데이터는 단일 리전 유지(코드 데이터의 주권·일관성이 지연보다 중요)
- 샌드박스: Docker → Firecracker microVM (멀티테넌트 격리 강화 + 125ms 콜드스타트)

핵심 원칙: **상태를 가진 것(PG/Redis)은 수직+관리형으로, 상태 없는 것(api/worker/ws)은 수평으로.**

## 13. 비용 분석 (월간, USD, 추정)

전제: 활성 사용자당 하루 20 요청, 요청당 평균 입력 6k/출력 1.2k 토큰, 블렌디드 단가(라우팅 후) 입력 $1.2/M, 출력 $6/M.

| 항목 | 1k users | 10k users | 100k users |
|---|---|---|---|
| LLM 추론 (원시) | $8,600 | $86,000 | $860,000 |
| └ 프롬프트 캐시 적중 60% 반영 | **$4,300** | **$43,000** | **$430,000** |
| └ 저가 라우팅(요약·간단질의 40%를 1/10 단가로) | **$2,900** | **$29,000** | **$290,000** |
| 임베딩 (인덱싱+쿼리) | $150 | $1,200 | $9,000 |
| Supabase (PG+Auth+Storage) | $100 | $700 | $4,000 |
| Redis (관리형) | $50 | $400 | $2,500 |
| 컴퓨트 (api/worker/sandbox) | $300 | $2,000 | $15,000 |
| 관측성/기타 | $100 | $800 | $5,000 |
| **합계** | **~$3.6k** | **~$34k** | **~$326k** |
| 사용자당 원가 | $3.6 | $3.4 | $3.3 |

결론 3가지:
1. **비용의 85%+가 LLM 추론.** 인프라 최적화보다 라우터의 저가 라우팅과 프롬프트 캐시 적중률이 손익을 결정한다. Prompt Engine이 prefix를 안정화한 이유가 바로 이것.
2. 사용자당 원가 ~$3.3 → Pro $20 요금제의 매출총이익 ~83%. 단 파워유저 롱테일이 원가를 지배하므로 플랜별 토큰 쿼터(plans.included_tokens)가 필수 방어선.
3. 임베딩은 증분 인덱싱 덕에 무시 가능한 수준으로 유지됨 — 전량 재인덱싱 설계였다면 10배 이상.

## 14. 병목 분석

### 14.0 실측 데이터 (Phase 6, 2026-08-02, M-series Mac / 로컬 PG17 + Redis 8)

계층별 처리량과 지연을 실제 부하로 측정했다. 재현: `pnpm --filter @aios/verify phase6`.

| 계층 | 부하 | p50 | p95 | p99 | 처리량 |
|---|---|---|---|---|---|
| STM append (Redis) | 1000회 / 동시 50 | 1ms | 3ms | 5ms | 38,462 rps |
| **STM getWindow (1000-메시지 윈도우)** | 500회 / 동시 50 | **22ms** | 27ms | 29ms | 2,083 rps |
| LTM remember (pgvector) | 500회 / 동시 20 | 31ms | 41ms | 49ms | 631 rps |
| LTM recall (500 벡터) | 1000회 / 동시 25 | 6ms | 30ms | 36ms | 2,141 rps |
| RAG 하이브리드 검색 (780 청크) | 300회 / 동시 20 | 15ms | 18ms | 20ms | 1,299 rps |
| 프롬프트 조립 (CPU) | 1000회 / 단일 | <1ms | <1ms | 1ms | 30,303/s |
| 도구 실행 (read_file) | 1000회 / 동시 25 | 1ms | 2ms | 3ms | 17,857 rps |
| **LLM 스트림 (Claude)** | 12회 / 동시 6 | **863ms** | 1,861ms | — | 4 rps |
| LLM TTFT (thinking ON, opus-5) | — | **15,097ms** | — | — | — |

리소스: 약 4,800회 연산 후 heap 34MB(증가분 23.5MB), CPU 1.44s user. PG 커넥션 8개(풀 상한 도달, 대기 0).

**세 가지 결론:**
1. **LLM이 지연의 28배를 지배한다** (863ms vs 우리 최대 31ms). 12장의 스케일링 우선순위와 13장의 비용 분석이 실측으로 확증됐다 — 우리 코드 최적화는 사용자 체감에 거의 기여하지 않는다.
2. **thinking-on 모델의 TTFT 15초는 대화형 UX에 치명적이다.** 사고가 가시 텍스트보다 먼저 소비되기 때문. 완화: (a) `thinking_delta` 이벤트를 SSE로 흘려 "생각 중"을 즉시 표시, (b) 저가/요약 작업은 라우터가 사고를 자동 비활성화, (c) 대화형 경로는 `reasoning: "off"` 또는 낮은 tier 모델 사용.
3. **증분 인덱싱이 99% 비용을 없앤다** — 60파일 최초 1,468ms vs 재스캔 8ms, 재임베딩 0회. 13장에서 임베딩을 무시 가능하다고 본 근거가 실측으로 확인됐다.

### 14.1 병목 순위

| # | 병목 | 증상 | 완화책 (적용 위치) |
|---|---|---|---|
| 1 | LLM TTFT/지연 | 실측 p50 863ms, thinking-on TTFT 15s — 전체 지연의 96% | 스트리밍 우선 설계, `thinking_delta` 조기 표시, 라우터 EWMA로 느린 프로바이더 회피, 병렬 컨텍스트 수집 |
| 1b | **STM 윈도우 읽기 (신규, 실측)** | 1000-메시지 윈도우에서 p50 22ms — 우리 계층 중 최악. 매 요청 경로에 있다 | 압축이 윈도우를 예산 내로 유지하는 것이 곧 성능 대책이다(기능이자 최적화). 추가 개선: LRANGE 범위 조회로 O(예산) 전환 |
| 2 | 프로바이더 429/529 | 버스트 시 실패율 급증 | 서킷브레이커+폴백 체인(router.ts), 조직별 rate limit로 상류 보호 |
| 3 | pgvector 검색 | 청크 1천만+에서 p95 상승 | project_id 필터가 탐색공간을 항상 축소, HNSW ef_search 튜닝, Phase 3 샤딩 |
| 4 | 임베딩 처리량 | 대형 리포 초기 인덱싱 수십 분 | 배치 64 + 동시성 제한, 증분화로 초기 1회만 비쌈, 진행률 WS 푸시로 UX 방어 |
| 5 | PG 커넥션 고갈 | 노드 확장 시 `too many connections` | pgbouncer transaction mode, 노드당 풀 상한 10 |
| 6 | Docker 콜드스타트 | 도구 실행 +300~800ms | 워밍 컨테이너 풀, 세션 단위 컨테이너 재사용(TTL 5분) |
| 7 | WS 팬아웃 | 대형 org 브로드캐스트 시 CPU 스파이크 | 채널 단위 PubSub(전역 브로드캐스트 없음), 메시지 배칭 16ms |
| 8 | Redis 단일 스레드 | STM 대량 append 시 지연 | 파이프라이닝, 키 설계로 클러스터 샤딩 가능(세션 키 = 해시태그) |
| 9 | 요약(compaction) 지연 | STM 압축이 hot path 진입 시 응답 지연 | 압축을 임계 80%에서 **선제적으로 백그라운드** 실행 |

측정 없이는 최적화 없음: 모든 경계(라우터, 도구, 메모리, 검색)에 OpenTelemetry span을 심고, 병목 순위는 분기마다 실측으로 갱신한다.
