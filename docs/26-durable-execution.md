# 로컬 승인·복구 내구성 보완

2026-09-12. 현재 Mac/T7의 안전한 단일 API 운영을 위한 보완이며 분산 운영·전원 차단 무손실 보장이 아니다.

## 발견한 결함과 변경

1. 기존 시작기 잠금은 포트별이었다. 같은 작업 폴더를 다른 포트/DB 설정으로 열면 프로세스별 메모리 잠금을 우회할 수 있었다. `main.ts`가 DB 연결 전에 실제 작업 폴더의 소유권을 선점하고, 정상 종료에서는 HTTP 작업·자원 종료 뒤 해제한다. 별도 서비스 객체도 같은 프로세스의 workspace 잠금을 공유한다.
2. 파일 복구 직후 DB 기록 저장이 실패하면 이미 원본으로 돌아간 파일도 재시도에서 영구 충돌했다. 이제 DB의 `restoring` 의도를 먼저 저장하고, 재시도는 현재 파일이 변경 후 해시인지 원본 해시인지 검사한다. 제3의 내용은 덮어쓰지 않는다. action/run 복구 완료는 하나의 SQL 문으로 기록한다.
3. 복구 DB commit은 끝났으나 응답만 유실된 경우, 반복 요청은 현재 원본 해시를 검사하고 파일을 다시 쓰지 않는다. 복구 뒤 다시 수정한 파일은 충돌로 보존한다. 새 파일의 복구는 부재 상태도 확인한다.
4. 재시작으로 끊긴 run과 남은 승인 action의 `interrupted` 기록도 하나의 SQL 문으로 갱신한다. 이전 승인은 메모리 대기자가 없으므로 재사용되지 않는다. 실행 기록은 insert를 기다리기 전에 활성 등록하여 조회와 시작 사이의 틈을 줄였다.
5. 통합 백업은 maintenance를 잡은 뒤 포트·DB 연결뿐 아니라 해당 workspace의 API 소유권도 검사한다. API는 소유권을 잡은 뒤 maintenance를 검사한다. 두 경계가 교차 검사하므로 직접 API 시작과 백업이 동시에 허용되지 않는다.

기존 DB 스키마의 text 상태와 기존 `restored_at`을 사용한다. 운영 DB 마이그레이션·운영 파일 복원은 하지 않았다.

## 소유권 계약과 잠금 진단

- `realpath(workspace)`의 NFC 정규화 SHA256를 키로 쓴다. 포트·DB URL·소스 checkout은 키에 포함하지 않는다. 비밀 설정의 값이나 해시는 저장하지 않는다.
- 위치: `<실제 workspace의 상위 두 단계>/run/local-api/<키>.lock`. 사용자 기본 workspace에서는 `/Volumes/T7/bigdata/run/local-api/` 아래다. 모델이 접근하는 workspace 밖에 둔다.
- 기록은 버전·실제 workspace 경로·호스트명·PID·프로세스 생성시각·무작위 소유 토큰이다. 살아 있는 소유자는 시간 경과로 만료시키지 않는다.
- `process.kill(pid, 0)` 및 제한 시간 2.5초의 `ps lstart`로 사망/PID 재사용을 실제 확인한 경우에만 회수한다. 어떤 PID에도 종료 신호를 보내지 않는다. 별도 `.lock.recovery` 디렉터리로 회수 경쟁을 직렬화한다.
- 깨진 JSON, 잠금 파일/조상 디렉터리/회수 경로의 링크, 다른 호스트/폴더 기록, 조회 권한 부족, 남은 회수 잠금은 자동 삭제하지 않는다. 시작 실패는 `local_api_busy`, `local_api_lock_unknown`, `local_api_maintenance`와 고정된 비밀 없는 안내로 종료한다.
- 기존 포트별 시작기 잠금과 API workspace 소유권은 서로 대체하지 않는다. 시작기는 관리하는 자식 프로세스/포트 소유권을 확인하고, API 잠금은 포트가 달라도 동일 폴더를 배제한다.

잠금 때문에 시작되지 않으면 다음 순서로 확인한다.

1. 이미 실행 중이면 `AIOS 상태 확인.command`로 확인하고 그 앱을 사용한다. 종료하려면 `AIOS 종료.command`로 정상 종료한다. DB·Redis·Ollama를 지우거나 내리지 않는다.
2. `local_api_maintenance`이면 백업/복원 검사 작업이 완료됐는지 확인한다. 유지보수 디렉터리를 지워 우회하지 않는다.
3. 비정상 API 종료 후 같은 Mac에서 다시 시작하면, 유효한 이전 기록의 프로세스가 실제 사망한 경우만 자동 회수한다. 재시작 뒤 변경 기록에서 중단된 실행을 확인한다. 승인을 다시 보낸다고 옛 작업이 실행되지 않는다.
4. `local_api_lock_unknown`이면 해당 workspace의 정확한 잠금 파일과 `.recovery` 유무, 기록된 호스트/PID/생성시각을 점검한다. 기록 PID는 `ps -p <PID> -o pid=,lstart=`로 비교한다. PID 번호만 보고 다른 프로그램을 종료하지 않는다.
5. 깨짐·다른 Mac의 기록·회수 도중 중단 때문에 확인할 수 없으면 잠금을 그대로 보존하고 점검을 요청한다. 모든 관련 API가 종료됐다는 별도 근거와 승인 없이 잠금 삭제/이동을 자동화하지 않는다. `run/`, checkpoint, DB, workspace 디렉터리 전체 삭제는 복구 방법이 아니다.

## 아직 보장하지 않는 것

- 위 다중 프로세스 시험은 실제 소유권 모듈과 HTTP fixture를 사용하는 시험이다. 아래 실제 운영 진입점 확인과 구분한다.
- 동일한 실제 workspace를 한 API에 묶는 경계다. 서로 다른 workspace에 같은 DB를 연결하는 임의 다중 API 구성이나 상위/하위가 겹치는 workspace, 여러 머신의 분산 운영을 지원한다고 주장하지 않는다.
- 파일 교체와 DB commit을 하나의 물리적 트랜잭션으로 만들지는 않는다. 영속 복구 의도와 현재 해시로 명시적 재시도를 안전하게 처리한다. 전원 차단·디스크 분리·파일시스템 고장 무손실은 검증하지 않았다.
- 악의적인 호스트 프로그램이 잠금 파일이나 경로를 동시에 바꾸는 공격, 호스트의 임의 파일 변경 경쟁, DB/외부 서비스/삭제·이동·권한 변경 롤백은 보장하지 않는다.
- 복구 뒤 이전 동작 검증은 유효하지 않다. 다시 지정 검증을 실행해야 한다. 시험 개수가 제품 점수나 사용자의 실제 작업 성공률을 직접 결정하지 않는다.
