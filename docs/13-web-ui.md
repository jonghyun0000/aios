# 웹 UI

Sprint #3 종료 시점의 정직한 결론은 "완성된 백엔드 플랫폼이지만 제품은 아니다"였다.
네 기능 모두 API만 존재하고 사람이 쓸 화면이 없었기 때문이다. 이 문서는 그 공백을 메운 작업이다.

측정 일자: 2026-08-23 · 검증 환경: macOS(darwin 25.6) · Node 22.18 · 실제 브라우저 + Docker 이미지

## 2. 설계 결정과 그 이유

### 2.1 API와 같은 오리진에서 서빙한다

`@fastify/static`으로 API 프로세스가 SPA를 서빙한다. 별도 CDN/nginx가 아니다.

이유는 성능이 아니라 **보안**이다. OAuth 세션이 `HttpOnly` + `SameSite=Lax` 쿠키인데,
UI와 API가 다른 오리진이면 브라우저가 이 쿠키를 API 요청에 붙이지 않는다.
동작시키려면 CORS를 열고 `SameSite=None`으로 낮춰야 하는데, 그건 CSRF 방어를 스스로 내리는 것이다.
파일 몇 개를 서빙하는 비용이 그 대가보다 훨씬 싸다.

개발 서버(Vite)도 같은 구조를 프록시로 재현한다 — "개발에서만 되는 인증"을 만들지 않기 위해서다.

캐시 정책:
- `index.html` → `no-cache`. 캐시되면 새 배포가 사용자에게 영영 도달하지 않는다.
- `/assets/*` → `max-age=31536000, immutable`. 내용이 바뀌면 파일명(해시)이 바뀌므로 안전하다.

### 2.2 의존성을 최소로 유지했다

| 넣지 않은 것 | 대신 | 이유 |
|---|---|---|
| react-router | 해시 라우터 90줄 | 필요한 것은 "경로→화면"과 파라미터 하나뿐 |
| react-query | `useAsync` 훅 45줄 | 캐시 무효화·낙관적 업데이트를 쓰지 않는다 |
| Tailwind / CSS-in-JS | 손으로 쓴 CSS, 토큰 12개 | 화면 7개에 빌드 파이프라인을 하나 더 얹을 이유가 없다 |
| y-websocket | 프로바이더 170줄 | 서버 프레이밍을 우리가 이미 구현했다. 재연결·인증 정책을 남에게 넘기지 않는다 |

이 저장소가 AI 프로바이더 SDK를 쓰지 않는 것과 같은 기준이다. 반대로
**eslint-plugin-react-hooks는 넣었다** — `exhaustive-deps`가 잡는 것은 스타일이 아니라
"클로저가 낡은 상태를 붙잡는" 재현 어려운 버그다.

### 2.3 textarea ↔ Yjs 바인딩

순진한 구현("입력마다 Y.Text를 통째로 교체")은 두 가지로 틀린다:
- 전체 교체는 `delete(전체) + insert(전체)`라 **동시에 편집 중인 상대의 변경을 전부 덮어쓴다.** CRDT를 쓰는 의미가 사라진다.
- 커서가 매 입력마다 끝으로 튄다.

그래서 공통 접두사·접미사를 잘라 **실제 바뀐 구간만** 계산해 적용한다(`diffText`).
IME 조합, 붙여넣기, 다중 삭제가 모두 이 하나로 처리된다. 한 트랜잭션으로 묶는 이유는
delete와 insert가 나뉘면 상대 화면에 "지워지기만 한 중간 상태"가 잠깐 보이기 때문이다.

**커서 보정**(`transformCaret`)이 없으면 문서 앞부분을 편집하는 동료가 있을 때
내 커서가 계속 엉뚱한 곳을 가리켜 타이핑이 불가능해진다. 실제 브라우저에서 확인했다:
커서 36에서 상대가 앞에 7자를 넣자 정확히 43으로 이동했다.

## 4. UI를 붙이면서 드러난 결함 5건

전부 "만들어서 실제로 써 봤기 때문에" 발견됐다.

### 4.1 전역 인증 훅이 UI 자체를 가로챘다 (치명)

훅이 모든 요청에 인증을 요구해 `/` 조차 401이었다. **로그인 화면을 받을 수 없으니 아무도 로그인할 수 없는** 상태.
→ 인증을 `/v1/*` 표면에만 건다. `s3:webui`가 재발을 막는다.

### 4.2 메시지 하나가 앱 전체를 백지로 만들었다 (치명)

`messages.content`는 문자열이 아니라 `{text, toolCalls}` **jsonb**다. 그대로 렌더링해
React error #31이 났고, React는 렌더 예외 시 트리 전체를 언마운트하므로 **사이드바까지 사라져
다른 페이지로 이동조차 불가능**했다.

두 가지를 고쳤다:
1. `messageText()`로 정규화 — 알 수 없는 형태는 빈 문자열이 아니라 JSON으로 보여준다(조용히 사라지면 디버깅이 불가능하다).
2. `ErrorBoundary` 도입 — 경계를 **콘텐츠에만** 두고 사이드바 바깥에 두지 않았다. 한 화면이 죽어도 나머지는 써야 한다.

### 4.3 채팅 에러가 표시되자마자 사라졌다

스트림 종료 시 `setLive(null)`이 에러까지 함께 지웠다. 사용자 눈에는 **"보냈는데 아무 일도 안 일어남"**.
→ 스트림 에러를 ref로 붙잡아 영구 표시 영역으로 옮긴다. 프로바이더 계정 문제는
"이것은 AIOS 자체의 오류가 아닙니다"라고 명시한다.

### 4.4 `/v1/models` 응답 형태를 잘못 가정했다

`{id, available}`이 아니라 `{model, provider, open, successRate, ewmaLatencyMs}`였다.
`open`은 **부정형**(서킷 열림 = 사용 불가)이라 화면에서 뒤집어야 한다.
결과적으로 성공률·지연까지 보여줄 수 있게 됐다.

### 4.5 Docker 이미지 빌드가 로컬과 달랐다

`vitest.shared.ts`를 COPY하지 않아 이미지 안에서만 TS2307로 실패했다.
→ 복사. 이미지 빌드가 로컬 빌드와 다르면 CI에서만 터지는 문제가 된다.

## 5. 의도적으로 남긴 마찰: API 키 로그인은 탭 단위

새 탭을 열면 다시 로그인해야 한다. 이유는 API 키를 `sessionStorage`에 두기 때문이다.

여기서 정직해야 할 점: **sessionStorage는 XSS에 대해 localStorage보다 안전하지 않다.**
둘 다 같은 오리진의 스크립트가 읽는다. 실제 차이는 수명뿐이다.
그래서 "이 브라우저에서 로그인 유지" 체크박스로 사용자가 고르게 했고, 기본값은 탭 한정으로 뒀다.

진짜 해법은 OAuth다 — HttpOnly 쿠키는 JavaScript가 아예 읽을 수 없고 탭 간에도 공유된다.
로그인 화면이 그렇게 안내한다.

## 11. 모바일 반응형

375px 기기에서 확인해 보니 **사용 불가 수준**이었다:

- 사이드바 232px 고정 → 화면의 **62%**를 차지
- 본문이 143px로 눌려 `6,597개 통계 / 표 ·` 처럼 글자가 한 자씩 줄바꿈
- 표가 화면 밖으로 넘쳐 열이 보이지 않음
- 검색 입력이 잘림

### 햄버거 메뉴를 쓰지 않은 이유

토글 상태를 JS로 관리하면 라우팅마다 닫아주는 처리가 필요하고, 열린 채로 페이지를
떠나는 버그가 생긴다. 항목이 6개뿐이라 **상단 가로 스크롤 내비**로 충분하다 —
상태가 없으므로 그런 버그가 존재할 수 없다.

```css
@media (max-width: 760px) {
  .shell { grid-template-columns: 1fr; grid-template-rows: auto 1fr; }
  .sidebar { flex-direction: row; overflow-x: auto; border-bottom: 1px solid var(--border); }
  table { display: block; overflow-x: auto; white-space: nowrap; }
}
```

표는 **열을 숨기지 않고 가로 스크롤**시킨다. 숨기면 사용자가 데이터가 있다는 사실조차 모른다.

### 차트 라벨 겹침 — 두 번 고쳤다

좁은 화면에서 `1999-01-01 00:00`과 `03 19:00`이 겹쳤다.

첫 시도는 첫 라벨 폭만 빼는 것이었는데 **여전히 겹쳤다.** 원인은 정렬 방식이다:
첫 라벨은 `text-anchor="start"`라 오른쪽으로 뻗고, 나머지는 `middle`이라
자기 위치에서 **왼쪽으로도 절반이 파고든다.** 그 절반을 계산에 넣지 않았다.

축약 후 길이는 미리 알 수 없으므로 최악(축약 없음)으로 잡았다 —
라벨 몇 개 줄어드는 손해가 겹쳐서 못 읽는 것보다 낫다.

```
needed = fullW * 1.5 + 8
```

검증은 눈이 아니라 **좌표로** 했다. 각 라벨의 좌우 경계를 계산해 겹침 픽셀을 셌다:

```
375px: ["1999-01-01 00:00","05 03:00","09 07:00","13 11:00"]  겹침 0px
```

### 검증

`s3:webui` 에 반응형 항목을 추가했다 (22 → **26개 검사, PASS 26/26**).
CSS가 빌드에서 누락되면 화면으로만 알 수 있으므로, 번들에 미디어 쿼리·1열 그리드·
가로 스크롤이 실제로 들어갔는지 고정한다.

## 12. 접근성

추측이 아니라 브라우저에서 실제로 측정한 뒤 고쳤다.

### 측정된 문제

| 문제 | 실측 |
|---|---|
| 라벨 없는 폼 필드 | **9개** (data 3, data 상세 2, chat 1, marketplace 2) |
| 버튼·링크 포커스 표시 | **전무** (`outline: none`) — 입력 필드에만 있었다 |
| 차트 대체 텍스트 | 없음 — 스크린리더가 아무것도 읽지 못함 |
| 본문 바로가기 | 없음 — 매 페이지 Tab 6번 |

`nav`·`main` 랜드마크와 `<h1>`, `lang="ko"` 는 이미 정상이었다.

### placeholder는 라벨이 아니다

9개 필드에 `placeholder` 는 있었다. 하지만 placeholder 는 **입력을 시작하면 사라지고**,
스크린리더가 안정적으로 읽어준다는 보장도 없다. 전부 `aria-label` 을 붙였다.

### :focus 가 아니라 :focus-visible

```css
:focus-visible { outline: 2px solid var(--accent); outline-offset: 2px; }
```

`:focus` 로 하면 **마우스 클릭에도 테두리가 남는다.** 그러면 보기 싫어서 결국
`outline: none` 으로 되돌리게 되고, 손해는 키보드 사용자만 본다.
`:focus-visible` 은 키보드 조작일 때만 켜지므로 그 충돌이 없다.

실제 Tab 키로 확인했다 — 내비 항목에 보라색 테두리가 나타난다.
(`element.focus()` 로는 `:focus-visible` 이 켜지지 않아 JS 측정만으로는 확인할 수 없었다.)

### 차트: 요약 + 데이터 표

선 그래프는 스크린리더에 **아무 정보도 주지 못한다.** 두 겹으로 제공한다:

1. `role="img"` + 실제 수치로 만든 요약
   ```
   시계열 선 그래프. 1999-01-01 00:00부터 1999-01-17 14:00까지 400개 시점.
   11.75에서 시작해 9.57로 끝남. 최저 4.15, 최고 19.8 (단위 °C).
   ```
2. 시각적으로 숨긴 데이터 표(`.sr-only`) — 요약만으로는 특정 시점의 값을 알 수 없다.
   전체 400행이 아니라 **x축에 라벨이 붙은 지점만** 넣는다. 차트에서 눈금으로
   읽을 수 있는 것과 같은 정보량이고, 수백 행을 읽히면 오히려 쓸 수 없다.

### 본문 바로가기

내비가 6개라 매 페이지마다 Tab 을 6번 눌러야 본문에 닿는다.
평소 화면 밖에 있다가 포커스를 받으면 나타나는 링크를 탭 순서 **맨 앞**에 뒀다.

해시 라우터를 쓰므로 `href="#main"` 은 라우팅을 건드린다 —
클릭을 가로채 직접 포커스를 옮기고, `<main>` 에 `tabIndex={-1}` 을 줬다
(그것이 없으면 프로그램적으로 포커스를 받을 수 없다).

### 그 밖에

- `aria-current="page"` — 현재 위치를 색으로만 표시하면 스크린리더 사용자는 알 수 없다
- `prefers-reduced-motion` — 움직임에 민감한 사용자를 위해 전환 효과 제거

### 검증

`s3:webui` 에 8개 항목 추가 (26 → **34개, PASS 34/34**).
CSS·JS 번들에 `:focus-visible`, `.skip-link`, `.sr-only`, `aria-label`(10개),
`aria-current`, `role="img"` 가 실제로 들어갔는지 고정한다 —
빌드에서 누락되면 화면으로만 알 수 있기 때문이다.

### 남은 한계

실제 스크린리더(VoiceOver·NVDA)로 들어보지는 않았다. 구조와 속성이 올바른지는
확인했지만, **읽히는 순서와 말맛이 자연스러운지는 사람이 들어봐야 안다.**

(색 대비는 이후 자동 측정을 붙였다 — 아래 "색 대비 자동 측정" 절 참조.)

## 13. 브라우저 자동 회귀 (Playwright)

여기까지 UI 검증은 전부 사람이 클릭하고 스크린샷을 본 것이었다.
그러면 **다음 변경에서 깨져도 아무도 모른다.** 실제로 고친 버그들
(차트 라벨 겹침, 모바일 사이드바, 포커스 표시)이 다시 깨져도 알 방법이 없었다.

### 구성

`apps/web/e2e/` — 데스크톱(1280×800) · 모바일(390×844) 두 프로젝트, **각 17개 = 34개**.

| 파일 | 내용 |
|---|---|
| `smoke.spec.ts` | 로그인, 7개 화면 렌더, 404 |
| `data.spec.ts` | 검색·페이지네이션·차트·필터 |
| `regressions.spec.ts` | **실제로 깨졌던 것**들 |
| `responsive.spec.ts` | 모바일 레이아웃 |

브라우저 바이너리는 **T7**에 둔다(`PLAYWRIGHT_BROWSERS_PATH`). Mac 내장은 여유가 없다.

### "떴다"의 기준을 내용으로 잡았다

빈 껍데기도 스크린샷은 찍힌다. 그래서 화면마다 **의미 있는 내용**을 확인한다:

```ts
await expect(page.getByText(/모델 \(\d+개 사용 가능\)/)).toBeVisible();
await expect(page.getByText("이 화면을 표시할 수 없습니다")).toHaveCount(0);  // ErrorBoundary
expect(errors, `콘솔 에러: ${errors.join(" | ")}`).toHaveLength(0);
```

차트도 "svg 가 있다"가 아니라 **"선이 그려졌다"**를 본다:

```ts
const d = await path.getAttribute("d");
expect(d!.length).toBeGreaterThan(50);
```

### 회귀 테스트는 좌표로 검증한다

라벨 겹침은 눈으로는 애매하다. 각 라벨의 좌우 경계를 계산해 **겹침 픽셀을 센다** —
`text-anchor` 가 `start` 인지 `middle` 인지에 따라 경계가 다르다는 것까지 반영한다
(그 차이를 놓쳐서 처음 수정이 실패했다).

### 테스트가 진짜로 잡는지 확인했다

통과만 하는 테스트는 신뢰할 수 없다. **일부러 회귀를 주입해** 확인했다:

```
:focus-visible { outline: none }        →  "포커스 표시가 없다 — 키보드 사용자가 위치를 알 수 없다"
@media (max-width: 1px)                 →  "본문이 화면 대부분을 차지해야 한다"
2 failed, 1 passed
```

각각 올바른 메시지로 실패했다. 원복 후 34/34 통과.

### 설정에서 막힌 것 세 가지

**1. AppleDouble 이 또 걸렸다** (이 저장소에서 다섯 번째)
`._data.spec.ts` 가 테스트로 수집돼 `Unexpected character` 로 전체가 죽었다.
→ `testIgnore: ["**/._*"]`

**2. 산출물 디렉터리를 지우지 못했다 — 진짜 원인은 파일시스템이었다**
Playwright 는 실행마다 `test-results` 를 지우는데 exFAT 에서 `ENOTEMPTY` 로 실패했다.
그러면 **테스트 내용과 무관하게 전 케이스가 실패**한다. 모바일 17개가 전부 그렇게 죽어
원인이 코드에 있는 것처럼 보였다.
T7 으로 옮겨도 똑같았다 — **저장소도 T7 도 둘 다 exFAT** 이라 디스크를 바꾸는 것으로는
해결되지 않는다. 문제는 용량이 아니라 파일시스템이다.
→ 시스템 임시 디렉터리(APFS)로 이동

**3. iPhone 13 프리셋은 WebKit 을 요구한다**
Chromium 만 설치해 뒀더니 `Executable doesn't exist ... webkit-2336` 로 실패했다.
우리가 검증하려는 것은 **브라우저 엔진 차이가 아니라 반응형 레이아웃**이므로
Chromium 에 모바일 뷰포트만 씌웠다. WebKit 까지 받으면 설치가 2배가 되고
CI 시간도 그만큼 늘어난다 — 얻는 것에 비해 비싸다.

### vitest 와 영역 분리

`e2e/` 를 배제하지 않으면 vitest 가 `*.spec.ts` 를 수집해 `test is not defined` 로 실패한다.
두 러너의 전역 API가 다르기 때문이다. `vitest.config.ts` 에서 `**/e2e/**` 를 제외했다.

### 파이프라인

```bash
node scripts/verify-all.mjs typecheck lint unit build s3-webui s5-bigdata-api s6-collab-multi e2e
# VERIFY: PASS — 8 passed, 0 failed
```

## 14. 접근성 트리 검사 — 그리고 내가 할 수 없는 것

### 먼저: 스크린리더를 직접 듣지 못했다

- **VoiceOver** 는 설치돼 있지만 **음성으로 출력**한다. 나는 소리를 들을 수 없다.
- **NVDA** 는 Windows 전용이라 이 Mac 에 없다.
- 접근성 권한(TCC)이 없어 VoiceOver 를 제어할 수도 없다.

그래서 "들어봤다"고 말할 수 없다. 대신 **스크린리더가 실제로 소비하는 데이터**인
접근성 트리(AX tree)를 Chrome DevTools Protocol 로 받아 검사했다.
구조·이름·순서가 맞는지는 이것으로 확정된다. 낭독의 자연스러움은 아니다.

### 검사 결과

`Accessibility.getFullAXTree` 로 6개 화면을 떠서 `ignored` 노드를 빼면
스크린리더가 실제로 읽는 목록이 남는다.

| 항목 | 결과 |
|---|---|
| navigation·main 랜드마크 | 전 화면 존재 |
| 제목 단계 건너뜀 | 0건 |
| 이름 없는 인터랙티브 요소 | 0건 |
| **live region** | **전 화면 0개** ← 문제 |

정적 구조는 이미 정상이었다. 문제는 **동적 변화가 하나도 알려지지 않는다**는 것이었다.

### live region 이 없다는 것의 의미

채팅 응답이 스트리밍돼도, 오류가 떠도, 검색 결과가 바뀌어도
**스크린리더 사용자는 아무것도 듣지 못한다.** 정적 구조가 완벽해도 앱을 쓸 수 없게 만든다.

고친 것:

| 대상 | 역할 | 이유 |
|---|---|---|
| 오류 메시지 | `role="alert"` | assertive — 실패를 모른 채 기다리게 두는 것이 더 나쁘다 |
| 로딩·빈 결과 | `role="status"` | polite — 낭독을 끊지 않고 알린다 |
| 검색 결과 개수 | `role="status"` | 조작이 반영됐는지 알 수 없으면 멈춘 줄 안다 |
| 협업 연결 상태 | `role="status"` | 끊긴 걸 모르면 편집이 사라지는 줄 안다 |
| 채팅 진행 상태 | `role="status"` | 아래 참조 |

### 스트리밍에 aria-live 를 직접 걸면 안 된다

글자가 늘어날 때마다 **문장 전체를 처음부터 다시 읽는다.** 침묵보다 나쁘다.

그래서 본문이 아니라 **상태 변화만** 알린다. 답변 내용은 사용자가 원할 때 직접 탐색한다.
실제 낭독 순서를 MutationObserver 로 기록해 확인했다:

```
요청을 보냈습니다. 응답을 기다리는 중  →  응답 생성 중  →  응답이 완료되었습니다.
```

도구를 쓰면 `도구 bigdata_search 실행 중` 이 사이에 들어간다.

### 검사가 찾아낸 또 하나: 로딩 중에는 페이지 제목이 없었다

`/data/1978` 의 `<h1>` 이 `AsyncBoundary` **안에** 있어, 데이터가 오기 전에는
페이지에 제목이 아예 없었다. 스크린리더 사용자는 "불러오는 중"만 듣고
자기가 어느 페이지에 있는지 알 수 없다.

→ 제목을 경계 밖으로 옮기고, 이름을 알기 전에는 "통계표" 로 둔다.

부수적으로 E2E 헬퍼도 고쳤다. `networkidle` 은 요청이 끝났다는 뜻이지
React 가 그렸다는 뜻이 아니다 — `h1` 이 나타나는 것이 실제 렌더 신호다.
(고정 sleep 은 느린 기기에서 깨지고 빠른 기기에서 시간을 낭비한다.)

### 회귀 테스트

`e2e/a11y-tree.spec.ts` — E2E 34 → **41개**.

- 랜드마크 존재 + **이름** (여러 개일 때 이름이 없으면 구분하지 못한다)
- 제목 단계 건너뜀 없음
- 이름 없는 인터랙티브 요소 없음
- 검색 결과 변화가 낭독됨
- 채팅 상태가 **순서대로** 낭독됨 (실제 스트리밍을 돌려 확인)

## 즉시 참이 되는 대기 조건 — 통과하던 테스트가 사실은 아무것도 확인하지 않았다

접근성 테스트 "채팅 상태 변화가 순서대로 낭독된다" 가 어느 날 실패했다.
읽힌 마지막 문구가 완료가 아니라 대기 중이었다:

```
Expected pattern: /완료|실패|중단/
Received string:  "요청을 보냈습니다. 응답을 기다리는 중"
```

처음에는 제품 버그로 보였다 — 완료 알림이 사라진 것처럼. 실제 알림 시퀀스를 찍어 보니
관측된 변화가 **단 하나**였고, 테스트 전체가 4.4초 만에 끝나 있었다.
로컬 7B 모델은 한 응답에 40초가 걸린다. 즉 테스트는 스트림을 기다린 적이 없다.

원인은 대기 조건이었다:

```ts
await page.getByRole("button", { name: "전송" }).click();
await page.waitForFunction(
  () => document.querySelector(".composer button")?.textContent?.includes("전송"),
);
```

버튼은 스트리밍 중에만 "중단" 이 된다. 그런데 `waitForFunction` 의 **첫 평가가
React 리렌더보다 먼저** 일어난다. 그 순간 버튼은 아직 "전송" 이므로 조건이 즉시 참이 된다.
테스트는 클릭 직전 상태를 "완료" 로 읽고 통과해 버렸다.

그래서 이 테스트는 오랫동안 초록이었지만 **아무것도 검증하지 않았다.**
느린 실행에서만 우연히 드러났다.

고침 — 시작을 먼저 확인하고, 그 다음에 종료를 기다린다:

```ts
const composerBtn = page.locator(".composer button");
await expect(composerBtn).toHaveText("중단");                        // 스트림이 시작됐다
await expect(composerBtn).toHaveText("전송", { timeout: 280_000 });  // 스트림이 끝났다
```

고친 뒤 관측된 시퀀스 (실측):

```
[변경] "요청을 보냈습니다. 응답을 기다리는 중"   +0.2s
[변경] "응답 생성 중"                          +36s
[변경] "응답이 완료되었습니다."                 +36.3s
```

**결함 주입으로 검증했다.** 완료 알림(`setLastAnnouncement`)을 제거하니 테스트가
`Received string: "응답 생성 중"` 으로 실패했다 — 회귀를 실제로 잡는다.
고치기 전 코드였다면 이 결함을 그대로 통과시켰을 것이다.

교훈: **상태가 A→B→A 로 돌아오는 것을 기다릴 때, 되돌아온 A만 확인하면 출발 전 A와
구별되지 않는다.** 반드시 B를 먼저 관측해야 한다. 초록색 테스트가 검증을 뜻하지는 않는다.

## 색 대비 자동 측정 (WCAG 2.1 AA)

접근성 작업에서 구조(AX 트리·ARIA·포커스 순서)는 검증했지만 **대비는 재지 않았다.**
"남은 한계"에 그렇게 적어 두고 넘어갔던 항목이다.

대비를 사람이 눈으로 보면 "읽히긴 하네"로 넘어간다. 그런데 저시력·야외 화면·저품질
디스플레이에서는 그 차이가 읽힘과 못 읽힘을 가르고, **색은 리팩터링 한 번에 조용히 바뀐다.**

### 무엇을 재는가

`apps/web/e2e/contrast.spec.ts` — 라이트/다크 × 데스크톱/모바일 × 6개 화면.

| 대상 | 기준 | 근거 |
|---|---|---|
| 일반 텍스트 | 4.5:1 | WCAG 2.1 SC 1.4.3 |
| 큰 텍스트(24px+ 또는 18.66px+ bold) | 3:1 | 같음 |
| 포커스 표시 | 3:1 | SC 1.4.11 비텍스트 대비 |

측정에서 신경 쓴 것:

- **반투명 색 합성.** `rgba(...)` 텍스트는 뒤에 깔린 색과 합성해야 실제로 보이는 색이 된다.
  조상을 거슬러 올라가며 불투명해질 때까지 합성한다 — 그러지 않으면 없는 대비를 있다고 잰다.
- **자기 텍스트만.** 부모까지 세면 같은 글자를 여러 번 재고, 실제로는 자식이 덮어쓴
  색을 부모의 색으로 잘못 판정한다.
- **`.sr-only` 제외.** 화면에 보이지 않고 스크린리더만 읽는 것은 대비 대상이 아니다.
- **포커스는 실제로 Tab 을 눌러 잰다.** `:focus-visible` 은 키보드 포커스에만 걸리므로
  CSS 를 읽거나 마우스로 클릭해서는 확인할 수 없다.
- **표본 하한.** 측정 개수가 0이면 "대비가 완벽함"이 아니라 "수집기가 죽었음"이다.
  단언에 하한을 걸어 그 둘을 구분한다.

### 실측 결과

```
[light] 총 86개 색 조합 측정, 위반 0건       [light] 포커스 가능 요소 70개, 위반 0건
[dark]  총 88개 색 조합 측정, 위반 0건       [dark]  포커스 가능 요소 70개, 위반 0건
```

데스크톱·모바일 합쳐 **8개 테스트**가 매 실행마다 돈다.

### 실제로 하나 고쳤다 — 기준선에 0.01 로 걸쳐 있던 색

측정해 보니 라이트 테마의 최저가 **4.51:1** 이었다. 기준 4.5 를 넘기지만 여유가 0.01 이다.

```
--text-muted: #6b7280
  on #ffffff (본문)      4.83:1
  on #f6f7f9 (사이드바)  4.51:1   ← 여유 0.01
```

통과하긴 한다. 그러나 두 변수 중 어느 쪽을 한 단계만 건드려도 무너지는 자리이고,
이 색이 붙는 곳은 11~12px 보조 텍스트라 실제로 가장 읽기 어려운 조합이다.
게다가 다크 테마의 같은 역할 색은 6.49~7.43 으로 여유가 충분해 **비대칭**이 심했다.

`#5f6773` 로 옮겼다 — 사이드바에서 5.33:1(여유 0.83), 흰 배경에서 5.72:1 이면서
본문(`#17191c`)과의 구분은 그대로다. 라이트 테마 최저가 4.51 → 4.83 이 됐다.

### 회귀를 실제로 잡는지 — 결함 주입 2회

**텍스트 대비**: `--text-muted` 를 `#6b7280` → `#7b8290` 으로. 눈으로는 거의 구분되지 않는다.

```
[light] 총 89개 색 조합 측정, 위반 36건
  / <small> 3.6:1 (필요 4.5:1, 11px/400) rgb(123, 130, 144) on rgb(246, 247, 249) — "AI Operating System"
```

**포커스 표시**: 포커스 링 색을 배경과 거의 같게(`#f2f3f5`). 아웃라인은 그대로 존재한다.

```
[light] 포커스 가능 요소 70개 확인, 위반 70건
  / <a> "본문으로 건너뛰기" — 포커스 링 1.11:1 (필요 3:1) rgb(242, 243, 245) on rgb(255, 255, 255)
[dark]  포커스 가능 요소 70개 확인, 위반 0건   ← 같은 색이 어두운 배경에서는 잘 보인다
```

다크가 통과하는 것이 정상이다 — `#f2f3f5` 는 어두운 배경에서 오히려 대비가 높다.
**한 테마에서만 깨지는 결함을 두 테마를 다 재기 때문에 잡을 수 있었다.**

### 곁가지로 알게 된 것

첫 결함 주입에서 CSS 규칙을 잘못 건드려 우리 포커스 스타일이 통째로 빠졌는데,
그때 브라우저 기본 포커스 링이 드러났다:

```
rgb(0, 95, 204) on rgb(22, 25, 32) → 2.94:1   ← 다크 테마에서 기준 미달
```

즉 **우리가 포커스 스타일을 지우면 브라우저 기본값은 다크 테마에서 WCAG 를 만족하지 않는다.**
`outline: none` 을 쓰지 않는 이유가 하나 더 생겼다.

### 남은 것

- **hover/active/disabled 상태**는 재지 않았다. 포커스와 기본 상태만 본다.
- **차트 SVG 안의 색**(선·격자·라벨)은 텍스트 노드가 아니라 이 수집기에 걸리지 않는다.
  `LineChart` 는 `role="img"` + 숨은 데이터 표를 함께 내보내므로 정보 접근 자체는 막히지 않지만,
  시각적 대비는 미측정이다.
- **AAA(7:1)** 는 목표로 잡지 않았다. 현재 최저는 4.56:1 로 AA 는 넘고 AAA 는 아니다.
