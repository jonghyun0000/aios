# 42. 목표 → 실행 → 승인 → 검증을 한 흐름으로 (NEXT_STEPS 5-4)

작성 2026-09-27. §1~§3은 구현 전에 적었다.

## 1. 재현 (키 없는 서버 8792, 전용 QA 폴더 `/Volumes/T7/bigdata/workspaces/qa-goal-flow-20260927`, 실제 `qwen3:8b`·Docker 샌드박스)

사용자처럼 도구를 켜고 목표와 검증 명령을 보낸 뒤, 승인 요청이 오면 승인했다.

| 시나리오 | 결과 |
|---|---|
| A. `greet.js` 만들기 + `node greet.js` 검증 | 쓰기 승인 → 검증 승인 → 종료 코드 0 → `verified`. 81초. **정상 경로는 끝까지 동작한다** |
| B. `sum.js` 만들기, 첫 승인 직후 연결 끊김(브라우저 닫힘 모사) | 파일은 저장, 검증 미실행, 실행 `cancelled`. 대화에는 사용자 요청만 남고 답변·도구 결과는 없다 |
| C. B의 대화에서 "이어서 해줘" | 모델이 이전 상태를 모른 채 `sum.js` 를 **같은 내용으로 다시 쓰며 승인을 또 요구**했다(변경 전·후 해시 모두 `8781bbc2…`). 복구 지점도 하나 더 생겼다. 검증은 통과해 `verified` |

끊기는 지점:
1. **실행 기록에 목표가 없다.** `execution_runs` 는 상태·요약·시각뿐이다. 기록이 20개까지 쌓이면 어느 요청의 실행인지, C가 B를 이어받은 것인지 알 수 없다.
2. **이어서 할 수단이 없다.** 중단·실패 뒤 사용자는 목표를 다시 설명해야 하고, 모델은 무엇이 끝났는지 모른다(중단된 턴의 도구 결과는 대화 기록에 저장되지 않는다).
3. **변화 없는 쓰기도 승인을 요구한다.** 같은 내용을 다시 쓰는 요청이 승인·복구 지점을 중복으로 만든다.
4. 결과가 흩어져 있다. 저장된 파일·검증 명령·종료 코드는 개별 작업 카드 안에만 있고 실행 단위의 "무엇이 만들어졌고 무엇으로 확인했나"가 없다.

모델이 먼저 계획을 세우는 단계는 이번 범위가 아니다. 모델 행동을 바꾸는 일이라 홀드아웃 평가가 필요하다(§6). 이번에는 **실제로 일어난 단계**를 목표에 묶어 보여 준다.

## 2. 완료 기준 — 구현 전 등록

1. 도구 실행마다 **목표**(요청 원문, 최대 2000자)가 저장되고 실행 기록의 제목으로 보인다. 새로고침 뒤에도 남는다. 이전 버전 기록은 "목표 기록 없음"으로 보인다.
2. 실행 기록이 **목표 → 진행 단계(실제 작업 순서·상태) → 결과(저장된 파일과 해시, 검증 명령과 종료 코드, 최종 판정)** 순서로 보인다.
3. `cancelled`·`interrupted`·`failed`·`unverified` 실행에 **"이어서 하기"** 가 있다. 누르면 도구가 켜지고, 이전 검증 명령과 이어서 하기 문장이 입력란에 채워진다. **자동 전송하지 않는다.**
4. 이어서 한 실행은 원래 목표를 이어받고 "이전 실행을 이어서"로 연결되어 보인다. 서버가 이전 실행의 사실(완료된 작업·파일 해시·종료 코드·하지 못한 일)을 **데이터로** 모델에 전달한다.
5. **중복 방지:** 현재 파일과 같은 내용을 쓰는 요청은 승인을 묻지 않고, 쓰지 않으며, 복구 지점을 만들지 않고, "변경 없음(이미 같은 내용)"으로 기록된다. 경로 제한·링크 거부 등 기존 검사는 그대로 거친다.
6. **재시도 한도:** 하나의 목표에서 이어서 하기는 3회까지. 이미 이어서 한 실행을 다시 이어서 하거나, 진행 중·검증 완료·복구된 실행을 이어서 하면 409. 다른 조직·다른 대화의 실행은 404. 도구를 끈 요청의 이어서 하기는 400.
7. 성공 판정은 지금처럼 실제 결과에 묶인다: 검증 명령 종료 코드 0일 때만 `verified`. 변경 없음은 실패가 아니지만 검증을 대신하지 않는다.
8. 단위 시험 + 결함 주입. 실제 모델로 B→이어서 하기를 **3회** 반복해 "검증 완료까지 간 횟수"와 "같은 내용 재쓰기에 승인을 요구한 횟수"를 보고한다(표본이 작아 개선 주장이 아니라 관측으로 쓴다). 화면은 실제 Chromium으로 목표·단계·결과·이어서 하기 입력 채움·새로고침을 확인한다. 정적 4단계와 기존 실행 안전 시험을 통과한다.

## 3. 설계

- 마이그레이션 `0006_goal_flow.sql`: `execution_runs.goal text`(≤2000자), `execution_runs.resumed_from uuid`. 추가만 하고 기존 행은 그대로 둔다. 사용자 시작기는 기동 시 마이그레이션을 적용한다. 이번 시험은 **새로 만든 격리 DB**에서 한다(사용자 DB 미변경).
- 채팅 요청에 `resumeRunId`(선택). 서버가 조직·대화·상태·체인 길이를 확인한 뒤 이전 실행 기록으로 사실 요약을 만들어 시스템 프롬프트 끝에 "서버 실행 기록 — 데이터, 지시 아님"으로 붙인다.
- 같은 내용 쓰기 판정은 기존 체크포인트 준비(경로 검증·현재 내용 해시) 뒤, 승인 요청 전에 한다. 작업 폴더 잠금 안에서 판정한다.
