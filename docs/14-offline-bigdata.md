# API 키 없이 내 데이터로 운영하기

질문: "API키 없이 내가 가진 데이터로만 진행하고 싶은데 가능한가?"
답: **가능하다.** 이 문서는 그것을 실제로 동작시킨 기록이다.

측정 일자: 2026-08-23 · Apple M1 / 16GB · 외장 T7(exFAT, 554GB 여유)

---

## 0. 두 종류의 "API 키"

| 종류 | 필요 여부 | 근거 |
|---|---|---|
| 공공데이터 수집 키 (KOSIS·KMA·NAVER·서울) | **불필요** | 3.2GB가 이미 로컬에 수집돼 있다 |
| AI 프로바이더 키 (Anthropic·OpenAI 등) | **불필요** | 로컬 추론 서버(Ollama)로 대체했다 |

착수 시점에는 후자가 실제 제약이었다. 코드를 확인한 결과 두 곳에서 막혀 있었다:

- `apps/api/src/context.ts` — 어댑터가 0개면 **부팅 자체를 거부**한다(의도된 방어).
- `packages/ai/src/router.ts` — OpenAI/Gemini 어댑터가 없으면 `no_embedder`를 던진다.

둘 다 해결했다. 이제 `LOCAL_LLM_BASE_URL` 하나만 있으면 외부 키 없이 전부 동작한다.

## 1. 저장 위치 — 왜 전부 T7인가

| 저장소 | 여유 | 판단 |
|---|---|---|
| Mac 내장 | **13GB** | 데이터를 두면 부팅 디스크를 위협한다 |
| colima VM 디스크 | 19.5GB 중 10.6GB | 디스크 이미지 자체가 Mac 내장에 있다 |
| T7 외장 | **554GB** | 여기만 쓴다 |

그런데 T7은 **exFAT**이다. 이것이 설계를 강제했다:

- **Postgres를 T7에 올리면 안 된다.** exFAT은 하드링크가 없고 fsync durability를 보장하지 않는다. PostgreSQL은 둘 다 전제하므로 "당장은 되지만 언젠가 조용히 손상"된다.
- **Parquet은 안전하다.** write-once 파일이라 exFAT의 약점을 건드리지 않는다.

그래서 역할을 나눴다:

```
T7/bigdata/
  parquet/          566MB  ← 팩트 1.4억 행 + 카탈로그
  ollama-models/    4.4GB  ← LLM 가중치
  env/              1.5GB  ← Python venv
  _tmp/                    ← DuckDB 스필
  logs/
```

Postgres(colima)에는 **카탈로그 메타데이터와 임베딩만** 넣는다. 1억 4천만 개 숫자를
임베딩하는 것은 의미가 없다. 의미가 있는 것은 "어떤 통계표가 무엇을 담는가"이다.

작업 결과 Mac 내장 여유는 13GB → **14GB로 오히려 늘었다**(venv를 T7으로 옮겨서).

`build.py`의 `assert_on_t7()`이 이 원칙을 코드로 강제한다 — T7 밖 경로를 넘기면
조용히 Mac을 채우는 대신 즉시 실패한다.

### 1억 행 기준 스키마

시리즈마다 고정인 컬럼(출처·통계표·데이터명·단위·주기)을 팩트에서 빼고

인코딩을 감안해도 수백 MB가 낭비된다.

```
facts/<카테고리>/data.parquet
  series_id INT32 · category · value DOUBLE · raw_value
  region · region_code · sido · cls1..3 · item · period · period_value BIGINT

catalog.parquet
  series_id · category · source · table_code · series_name · unit · period_type
  period_min/max · row_count · region_count · item_count · null_count · rel_path
```

## 4. 적재 중 발견한 결함 4건

전부 "실제로 돌려봤기 때문에" 드러났다.

### 4.1 CSV 인용부호 자동 추정이 데이터를 갈랐다

DuckDB가 파일마다 인용 규칙을 따로 추정한다. OWID 파일에서 `quote=(empty)`로 잡아
`"Less developed regions, excluding China"` 안의 쉼표가 컬럼을 갈랐고 17번째 컬럼이 생겨
변환 전체가 실패했다.

`ignore_errors=true`로 넘기면 **그 행들이 조용히 사라진다.** 규칙을 명시적으로
고정하는 것이 유일한 정답이었다:

```python
CSV_OPTS = "header=true, all_varchar=true, delim=',', quote='\"', escape='\"'"
```

### 4.2 한글 유니코드 정규화 — 가장 위험했던 버그

macOS는 파일명을 **NFD**(자모 분리)로 돌려준다. `01_인구_사회`가 8코드포인트가 아니라
13코드포인트다. 반면 사람이 타이핑하는 한글은 **NFC**다.

결과: `where category = '01_인구_사회'` 가 **에러 없이 0행**을 반환했다.
조용히 틀린 답을 주는 것이 가장 위험하다.

원인은 두 단계였다:
1. `os.walk`는 NFC를 주는데, 내가 만든 디렉터리 `category=<이름>`을 DuckDB가
   **하이브 파티션으로 자동 인식**해 exFAT 디렉터리명(NFD)이 파일에 저장된 컬럼을 덮어썼다.
2. 그래서 (a) 디렉터리에서 `category=` 접두사를 빼고 (b) 읽기에서 `hive_partitioning=false`를
   명시하고 (c) 경로 유래 문자열을 전부 NFC로 정규화했다.

### 4.3 AppleDouble 사이드카가 Parquet 글로브에 걸렸다

exFAT에서 macOS가 남기는 `._data.parquet`이 `*.parquet`에 매칭되어
"No magic bytes found at end of file"로 모든 질의가 실패했다.
파일을 지워도 접근할 때마다 재생성되므로 글로브를 `*/data.parquet`으로 고정했다.
(이 저장소에서 마이그레이션·vitest·eslint에 이어 네 번째로 겪은 같은 원인이다.)

### 4.4 표본 추정이 2배 빗나갔다

30개 표본으로 6,900만 행을 추정했으나 실제는 **1억 4천만 행**이었다.
`10_건설_주택_토지` 한 카테고리가 987파일 6,879만 행으로 전체의 절반이었고
표본이 이를 잡지 못했다. 다행히 스키마를 1억 기준으로 설계해 두어 문제가 없었다.

## 5. 로컬 LLM 연결

### 추가한 것

| 파일 | 내용 |
|---|---|
| `packages/ai/src/providers/local.ts` | OpenAI 호환 서버 어댑터 (base URL만 교체) |
| `packages/ai/src/catalog.ts` | `localModels()` — 설정에서 모델 카탈로그 생성 |
| `packages/shared/src/types.ts` | `ProviderId`에 `"local"` 추가 |
| `packages/shared/src/env.ts` | `LOCAL_LLM_BASE_URL` 등 4개 |
| `apps/api/src/context.ts` | 어댑터 배선 + 부팅 거부 조건 완화 |
| `packages/ai/src/router.ts` | 임베딩 폴백에 local 우선 추가 |
| `scripts/set-embedding-dim.mjs` | 임베딩 차원 변경 |

`xai.ts`가 이미 같은 패턴(base URL만 바꾼 상속)을 쓰고 있어 그대로 따랐다.
호환 API를 재구현하면 두 코드 경로가 서로 다르게 썩는다.

### 설계 결정

**비용을 0으로 둔다** — 로컬 추론은 실제로 과금되지 않는다. 그 결과 라우터의 비용
점수에서 항상 최상위가 되어, 외부 모델과 함께 설정된 경우 cheap/summarize 작업이
자동으로 로컬로 흐른다. 의도된 동작이다.

**qualityTier를 1(최하)로 둔다** — 7B급 로컬 모델은 프런티어 모델보다 뚜렷이 약하다.
품질 우선 작업에서 외부 모델이 있으면 그쪽이 선택되어야 한다.

**임베딩은 local을 먼저 본다** — 로컬 서버를 설정했다는 것은 외부 호출을 원치 않는다는
뜻이고, 임베딩만 몰래 외부로 나가면 그 의도를 배신한다.

### 임베딩 차원 문제

0001 마이그레이션이 `vector(1536)`(OpenAI 기준)으로 고정돼 있어 bge-m3(1024차원)로
저장하면 `expected 1536 dimensions, not 1024`로 실패한다.

차원은 '어떤 임베더를 쓰는가'라는 **배포 시점 결정**이지 스키마의 고정 사실이 아니므로
`scripts/set-embedding-dim.mjs`로 분리했다. 기존 임베딩이 있으면 `--force` 없이는
거부한다 — 차원이 다른 벡터는 비교 자체가 불가능해서, 남겨두면 코사인 거리가
의미 없는 값을 내놓고 그것을 검색 결과라고 믿게 된다.

## 7. 재현 방법

```bash
# 1) 로컬 추론 서버 (모델은 T7에 저장)
export OLLAMA_MODELS=/Volumes/T7/bigdata/ollama-models
ollama serve &
ollama pull qwen2.5:7b-instruct && ollama pull bge-m3

# 2) 데이터 적재 (전부 T7)
PROJ="…/난제1(AI운영체제)"
/Volumes/T7/bigdata/env/bin/python $PROJ/tools/bigdata/build.py catalog   # 41초
/Volumes/T7/bigdata/env/bin/python $PROJ/tools/bigdata/build.py facts     # 45초
/Volumes/T7/bigdata/env/bin/python $PROJ/tools/bigdata/build.py enrich    #  2초
/Volumes/T7/bigdata/env/bin/python $PROJ/tools/bigdata/build.py verify    # 원본 대조

# 3) 임베딩 차원 맞추기 (bge-m3 = 1024)
EMBED_DIM=1024 node scripts/set-embedding-dim.mjs

# 4) AIOS 기동 — API 키 없이
export LOCAL_LLM_BASE_URL=http://127.0.0.1:11434/v1
export LOCAL_LLM_MODELS=qwen2.5:7b-instruct LOCAL_EMBED_MODEL=bge-m3
pnpm --filter @aios/api dev
```

데이터 질의는 DuckDB로 직접:

```sql
select f.period, avg(f.value)
from read_parquet('/Volumes/T7/bigdata/parquet/facts/*/data.parquet', hive_partitioning=false) f
join read_parquet('/Volumes/T7/bigdata/parquet/catalog.parquet') c using (series_id)
where c.series_name like '%전세가격지수%'
group by 1 order by 1 desc;
```

## 9. AI ↔ 데이터 연결 (Tool Engine)

§8에서 "아직 없다"고 적었던 부분을 구현했다. 이제 로컬 LLM이 1.4억 행에 직접 답한다.

### 도구 3개

| 도구 | 용도 |
|---|---|
| `bigdata_search` | 카탈로그에서 통계표 찾기 (부분일치 → 실패 시 의미검색) |
| `bigdata_series` | series_id의 시계열 조회 — SQL 없이 |
| `bigdata_query` | 읽기 전용 SQL (DuckDB 문법) |

### 왜 Parquet을 직접 읽지 않고 DuckDB 파일로 물질화했나 — 보안

AI에게 SQL을 맡기면 프롬프트 인젝션으로 다음이 시도된다고 가정해야 한다:
`read_csv('/etc/passwd')`, `COPY ... TO '/tmp/exfil'`, `INSTALL httpfs`(네트워크 유출),
`ATTACH '/다른/db'`.

DuckDB의 `enable_external_access=false`가 이를 한 번에 차단한다. **그런데 그 설정은
`read_parquet`도 함께 막는다.** 데이터를 DB 파일 안에 넣어두면 질의 시점에 파일 접근이
아예 필요 없어져 외부 접근을 완전히 꺼도 모든 분석 질의가 동작한다.

방어는 네 겹이다:

1. `access_mode: READ_ONLY` — 쓰기가 물리적으로 불가능
2. `enable_external_access: false` — 파일·네트워크 접근 차단
3. `lock_configuration: true` — 질의 안에서 SET으로 되돌리지 못하게
4. SELECT/WITH 단일 문장만 + 강제 LIMIT + 타임아웃

4번을 문자열 검사로만 하지 않는 이유: 문자열 필터는 우회당한다. 1~3번이 실제 방어이고
4번은 실수 방지용이다.

```
통과   집계 / 한글 조건 / 조인 / 연결 재사용
```

8종 전부 차단, 정상 질의는 전부 통과.

### 카탈로그 의미 검색

`bigdata_search`는 부분 문자열 일치가 먼저다. 실패하면 임베딩 유사도로 재시도한다.
사용자는 통계청이 붙인 정확한 명칭을 모르는 것이 정상이기 때문이다.

6,568개 통계표명을 bge-m3로 임베딩(194초, 34개/초)해 DuckDB 안의
`catalog_embeddings` 테이블(FLOAT[1024])에 저장했다. Postgres가 아니라 DuckDB에 두는
이유는 질의 시점에 조인이 필요 없고 도구가 이미 연 연결을 그대로 쓸 수 있어서다.

임베딩 대상 텍스트는 이름만이 아니라 `series_name | category | unit | source`다.
이름만으로는 '지수'와 '비율'처럼 비슷한 통계표가 구분되지 않는다.

실측: `"집값"` — 어느 통계표명에도 없는 구어체 — 로 검색하니
`주택가격`, `주택가격지수` 등을 유사도 0.622로 찾았다.

### 실제 동작 (로컬 LLM, API 키 없음)

```
질문: "전세가격 관련 통계표를 찾아줘"
  [도구] bigdata_search {"keyword": "전세가격"}
  [결과] 1978 유형별 전세가격지수 | 월 | 2003-12~2025-03 | 110,632행 …
  [답변] 통계표 목록을 한국어로 정리

질문: "series_id 1978의 2024년 시계열을 최근 5개만"
  [도구] bigdata_series {"series_id":1978,"period_prefix":"2024","limit":5,"order":"desc"}
  [답변] 2024-12: 94.232 / 2024-11: 94.227 / 2024-10: 94.153 …
         "전세가격지수 값이 주로 하락 추세를 보이고 있습니다"
```

### 여기서도 결함이 나왔다

**1. DuckDB 설정 잠금이 두 번째 연결을 죽였다**
`lock_configuration`은 인스턴스 전역인데 연결마다 `SET`을 걸었다. 첫 연결이 잠근 뒤
두 번째 연결의 같은 SET이 에러가 되어, **두 번째 도구 호출부터 실패**했다.
→ 인스턴스 생성 시 설정으로 한 번만 건다.

**2. 도구가 등록됐는데도 모델이 안 쓰는 것처럼 보였다**
원인은 모델이 아니라 `EADDRINUSE` — 구 프로세스가 포트를 잡고 있어 **도구 없는 예전
서버가 응답**하고 있었다. 부팅 로그에 등록된 도구 목록을 남기도록 고쳤다.
도구가 조용히 빠지면 "모델이 멍청하다"로 오진하게 된다.

**3. 7B 모델이 존재하지 않는 값으로 필터링했다**
`catalog.period_type = '년월'`(실제값 '월')로 SQL을 짜 0행을 받았다.
존재하지 않는 값으로 걸러도 SQL은 **성공**하므로 오류로 드러나지 않는다.
→ 가장 흔한 질문(시계열 조회)을 `bigdata_series` 파라미터 3개로 줄여 그 실패 경로를 없앴다.
빈 결과일 때는 실제 존재하는 시점 예시를 함께 돌려준다.

### 운영 주의

DuckDB 파일은 **읽기 전용 연결도 락을 잡는다.** AIOS가 떠 있는 동안에는
`build.py db` / `embed` 가 `Conflicting lock is held` 로 실패한다.
데이터를 다시 만들 때는 API 서버를 먼저 내려야 한다.

### 재현

```bash
/Volumes/T7/bigdata/env/bin/python tools/bigdata/build.py db      # Parquet → DuckDB (28초)
/Volumes/T7/bigdata/env/bin/python tools/bigdata/build.py embed   # 카탈로그 임베딩 (194초)
export BIGDATA_DB_PATH=/Volumes/T7/bigdata/bigdata.duckdb
pnpm --filter @aios/api dev
# 부팅 로그: [tools] … bigdata_search, bigdata_series, bigdata_query
```

**번들이 커지는 것보다 런타임에 죽는 것이 나쁘다.**

올바른 해법은 네이티브 패키지만 앱의 `package.json`에 직접 선언하는 것이다.
그러면 기존 external 로직이 자동으로 처리하고 `pnpm deploy` 가 런타임 트리에 넣는다.

## 11. 웹 UI 데이터 화면

1.4억 행을 만들어놓고 채팅으로만 접근할 수 있었다. 통계는 표와 차트로 봐야 한다.

### 추가한 것

| 계층 | 내용 |
|---|---|
| API | `GET /v1/bigdata/{categories, catalog, series/:id, series/:id/export}` |
| UI | `#/data` 카탈로그 브라우저, `#/data/:id` 시계열 상세 |
| 차트 | 인라인 SVG 라인 차트 (`components/LineChart.tsx`, 141줄) |

### 왜 HTTP 라우트가 SQL을 받지 않는가

도구(`bigdata_query`)는 LLM이 쓰고 격리 4겹으로 감싸져 있다. 하지만 브라우저에 SQL 창을
여는 것은 성격이 다르다 — 조직 구성원 누구나 무거운 질의로 서버를 마비시킬 수 있고,
그걸 막으려면 결국 또 다른 화이트리스트가 필요해진다.
여기서는 **필요한 질문 모양만 파라미터로** 노출했다.

### 왜 차트 라이브러리를 넣지 않았나

이 저장소가 react-router·react-query·Tailwind를 넣지 않은 것과 같은 기준이다.
필요한 것은 선 하나, 축 두 개, 호버 툴팁뿐인데 recharts는 수백 KB를 가져온다.
번들 증가는 **11KB**(262KB → 273KB)에 그쳤다.

직접 그릴 때 빼면 라이브러리보다 나빠지는 것들은 지켰다:
값 범위에 여백, 상수 시계열에서 0으로 나누지 않기, x축 라벨 솎아내기(최대 8개),
**결측 구간에서 선 끊기**(이으면 없는 데이터를 있는 것처럼 보여준다).

### 검증

`apps/verify/src/s5-bigdata-api.ts` — **31개 검사, PASS 31/31**.

s4(도구 직접 호출)와 나눈 이유는 DuckDB 파일 락이다. 읽기 전용 연결도 락을 잡으므로
s4는 서버가 **꺼져** 있어야 하고, s5는 **켜져** 있어야 한다. 둘은 배타적이다.

```bash
# 서버 켜고
AIOS_BASE_URL=http://127.0.0.1:8790 AIOS_API_KEY=… pnpm --filter @aios/verify s5:bigdata-api
# 서버 끄고

```

브라우저 실측: 6,568개 통계표 목록 → '전세가격' 검색 60건 → 상세 진입 →
223개 시점 차트 → 지역 '서울' 필터 적용 시 곡선 변화 → 호버 툴팁(2016-05 / 92.91 / 4개 관측 평균).

### 이번에 드러난 결함 5건

**1. `region_count`가 사용자를 속이고 있었다**
카탈로그가 `region_code`(전 행이 'KOR')를 세어 "지역 1"이라고 표시하면서,
드롭다운은 205개 지역을 고르게 했다. 지역명(`region`)을 세도록 고치고
`region_code_count`를 별도 필드로 남겼다.

**2. enrich가 멱등하지 않았다 — 그래서 1번 수정이 반영되지 않았다**
`select c.*` 가 이전 실행이 덧붙인 컬럼까지 포함해, 재실행마다
`region_count_1`, `region_count_2` … 가 쌓였다. **앞자리의 옛 값이 계속 이겨서
계산식을 고쳐도 결과가 그대로였다.** 기본 컬럼을 명시해 멱등성을 확보했다
(두 번 돌려 15컬럼 유지 확인).

**3. 페이지네이션에 중복이 있었다**
`row_count desc` 는 동점이 흔한데 타이브레이커가 없어 페이지마다 순서가 달라졌다.
1페이지와 2페이지에 같은 통계표가 겹쳐 나왔다. `, series_id asc` 를 추가했다.

**4. 잘못된 파라미터가 500으로 나갔다**
`?limit=99999` 같은 흔한 실수에 zod가 던진 에러가 매핑되지 않아 500이었다.
모니터링에서 진짜 장애와 구분되지 않는다. 전역 핸들러에서 `ZodError → 400`으로 매핑했다.

**5. CSV 링크에 API 키를 URL로 넣으려 했다**
`<a href>` 가 간단하지만 토큰이 브라우저 히스토리·리퍼러·서버 로그에 남는다.
fetch + Blob 방식으로 바꿨다.

### 오판했다가 되돌린 것

CSV의 UTF-8 BOM이 빠진 줄 알았다. 브라우저 `res.text()` 가 **규격상 BOM을 제거**하기
때문에 없는 것처럼 보였을 뿐, 실제 바이트는 `ef bb bf` 로 정상이었다.
검증 코드도 `arrayBuffer()` 로 바이트를 직접 보도록 고쳤다.

## 12. 해양관측 적재 — 데이터 완전성 100%

§8에서 "원본의 98.9%만 적재됐다"고 적었던 나머지 1.1%를 채웠다.
빠져 있던 것은 KMA 해양관측(부이·등표) 52개 파일이다.

### 왜 별도 변환기인가

92_정제의 KOSIS 데이터는 이미 long format(16컬럼)이라 그대로 옮기면 됐다.
해양관측은 **wide format 관측 원본**이다 — 한 행에 시각·지점과 15개 측정값이 나란히 있다.

```
TM,STN,WD1,WS1,WS1_GST,WD2,WS2,WS2_GST,PA,HM,TA,TW,WH_MAX,WH_SIG,WH_AVE,WP,WO,AQC,MQC
202501010000,21229,290,2.9,6.1,293,2.8,5.7,1018.9,49.0,6.3,15.3,3.1,2.3,1.3,6.9,348,…
```

long으로 녹이는 과정에서 결측 표기·물리 범위·단위를 항목마다 다르게 다뤄야 해서
`build.py`에 끼워 넣으면 두 갈래 로직이 한 함수에 섞인다. `tools/bigdata/marine.py`로 분리했다.

### 시리즈 정의: (계열, 측정항목)

파일 단위가 아니다. **한 시리즈는 하나의 측정 가능한 양**이어야 한다.
풍향(0~360°)과 수온(°C)을 한 시리즈에 담으면 평균·최대가 물리적으로 무의미해지고,
카탈로그의 `unit` 필드도 하나만 가질 수 있다.

결과: 부이 15개 + 등표 14개 = **29개 시리즈**가 전 연도(1996~2026)를 관통한다.

### 결측과 이상치를 구분했다

| 구분 | 처리 | 근거 |
|---|---|---|
| `-99` 계열 (≤ -90) | **행을 만들지 않음** | KMA 결측 표기. wide에서 빈 칸이던 것을 long에서 NULL 행으로 되살릴 이유가 없다 |
| 물리 범위 밖 | **행은 남기고 `value=NULL`, `raw_value` 보존** | 측정은 됐는데 값이 불가능하다. 조용히 지우면 사용자가 원본 이상을 모른다 |

임계값 -90의 근거는 실측이다: -90~-50 구간에 값이 사실상 없고(부이 기온 71건, 수온 9건),
그 아래는 전부 -99 계열이다. 실제 관측 최저는 기온 -49.7°C / 수온 -43.3°C였다.

범위 위반은 41,162건(부이 6.4M 중 0.6%)이었다. 적어 보이지만 **최대값 집계를 망친다** —
기압 10,355hPa, 기온 4,810°C, 풍향 7,013° 같은 값이 섞여 있었다.

의미를 확정하지 못한 `LS`·`VT`는 한글 이름을 붙이지 않고 원본 코드 그대로 뒀다.
틀린 이름을 붙이면 사용자가 그것을 사실로 믿는다.

## 13. 지역코드 표준화 검증 — 결론: 표준화되어 있지 않다

§8에 "출처별 코드 체계가 통일됐는지 미검증"으로 남겨둔 항목이다. 검증한 결과
**표준 지역코드는 존재하지 않는다.** 이것은 고칠 수 있는 버그가 아니라 원본 데이터의 성질이다.

### 세 겹의 문제

**1. `region_code`는 출처마다 다른 체계다**

| 출처 | 코드 종류 | 실제 내용 | 행수 |
|---|---:|---|---:|
| KOSIS | **1종** | 전부 `'KOR'` — 국가 코드 | 136,548,884 |
| KMA | 133종 | 관측소 번호 (`22101`=덕적도) | 111,920,219 |
| OWID | 293종 | ISO-3 국가코드 (`GBR`, `FRA`) | 846,364 |
| Eurostat | 64종 | NUTS 코드 | 2,653,515 |
| WorldBank | 264종 | ISO-3 | 118,359 |

KOSIS 1억 3,655만 행이 **전부 `'KOR'`** 이다. 서울이든 제주든 구분되지 않는다.
그런데 OWID·WorldBank에도 `KOR`(대한민국)이 있다 — 코드로 조인하면
**한국의 모든 지역 통계가 한국의 국가 통계와 붙는다.** 조용히, 에러 없이.

**2. 원본의 `지역코드원본`도 표준이 아니다**

변환 시 버렸던 컬럼을 확인해 보니, 통계표마다 완전히 다른 내부 코드였다:

```
131021127444100000000            용도별 토지거래
13102134568ORGANISATION_UNIT.Z24 지역별 기업경기실사지수
15315HJG008010                   도서관
A0307                            국세통계
11                               인구 (← 이것만 행정구역 코드)
```

길이가 2~32자로 제각각이고, 2자리(43종)만 시도 코드다. 21자리 코드가 180만 행이다.
**복구할 가치가 없어 그대로 두었다.**

**3. 지역명도 표기가 갈린다**

지역명 **7,660종**. 같은 곳에 이름이 여럿이다:

| 표기 | 행수 |
|---|---:|
| 서울특별시 | 972,852 |
| 서울 | 355,068 |
| 강원특별자치도 / 강원도 / 강원 | 545,324 / 434,255 / 338,644 |

`where region = '서울'` 로 조회하면 **서울특별시 97만 행을 조용히 놓친다.**
원본의 `sido` 컬럼은 23.5%만 채워져 있어 대안이 되지 못한다.

### 한 조치: `sido_norm` 파생 컬럼

`region` 에서 시도를 정규화한 컬럼을 DuckDB 계층에 추가했다.
Parquet은 원본에 충실하게 두고 분석 편의만 질의 계층이 제공한다 —
규칙이 바뀌어도 2.5억 행을 다시 만들 필요가 없다.

```sql
-- 표기와 무관하게 하나로 묶인다
select sido_norm, count(*) from facts where sido_norm = '서울' group by 1
```

**'광주'는 접두사 매칭에서 제외했다.** 광주광역시(985,417행)와 경기도 광주시(274,029행)가
충돌하기 때문이다. 정확히 `'광주'`이거나 `'광주광역시…'`일 때만 광주로 보고, `'광주시'`는 NULL로 남긴다.

### 정규화로도 해결되지 않는 것

KMA 제외 시 커버리지는 23.5% → 24.7%로 소폭 오른다. 나머지는 **원리적으로 결정 불가**다:

| 지역명 | 행수 | 문제 |
|---|---:|---|
| 동구 | 1,498,434 | 부산·대구·인천·광주·대전·울산 6곳에 존재 |
| 중구 | 1,491,535 | 6곳에 존재 |
| 고성군 | 536,894 | 강원·경남 양쪽에 존재 |

부모 시도 정보가 원본에 없으므로 추측해서 채우면 **조용히 틀린 집계**가 된다.
NULL로 남기는 것이 정직하다.

### AI가 틀리지 않도록

`bigdata_query` 도구 설명에 경고를 넣었다. 모델이 스키마만 보고
`join on region_code` 를 시도하는 것을 막기 위해서다:

- region_code로 조인하지 마라 (출처마다 다른 체계)
- 지역 필터는 `sido_norm` 을 써라
- 시군구명은 여러 시도에 존재하니 결과가 합쳐진 것일 수 있다고 사용자에게 알려라
- 해양관측의 region은 대부분 섬·해역 이름이라 sido_norm이 NULL이다 ('울산'·'인천' 부이는 예외)

### 남는 한계

이 데이터셋으로 **시군구 단위 지역 비교는 신뢰할 수 없다.** 시도 단위는 `sido_norm`으로 가능하다.
시군구가 필요하면 행정표준코드 매핑 테이블을 외부에서 가져와 지역명으로 조인해야 하는데,
그 조인 자체가 이름 표기 문제를 다시 만난다.


### 검증 결과 (DB 재빌드 후 실측)

```
region='서울'      →   355,068행
sido_norm='서울'   → 1,434,734행   (4.0배 — 서울특별시·서울 강동구 등이 함께 잡힌다)

강원 3가지 표기 통합: 강원특별자치도 545,324 / 강원도 434,255 / 강원 338,644
광주 충돌 안전 처리 : 광주광역시·광주 → '광주' / 광주시·광주군 → NULL
```

KMA 1억 1,192만 행 중 sido_norm이 붙은 것은 527만 행인데, 전부 **'울산'·'인천' 부이**다.
그 도시 앞바다에 있는 관측소이므로 오류가 아니다 — 처음에 "KMA는 전부 NULL"이라고
적었던 설명이 틀렸고, 코드가 아니라 문서를 고쳤다.

## 14. 모델 교체 검토 (1차) — 결론이 뒤집혔다: §16 참조

§8에 "qwen2.5:7b는 한국어 답변에 중국어가 섞인다"고 적었다. LG의 exaone3.5(한국어 특화)로
바꿀 수 있는지 검토했다.

### 결론: 바꿀 수 없다 — exaone3.5는 도구 호출을 지원하지 않는다

Ollama가 모델 능력을 직접 알려준다:

```
qwen2.5:7b-instruct   capabilities: ['completion', 'tools']
exaone3.5:7.8b        capabilities: ['completion']
```

도구를 포함해 요청하면 명시적으로 거부한다:

```
{"error":{"message":"registry.ollama.ai/library/exaone3.5:7.8b does not support tools"}}
```

**이 제품에서 도구 호출은 1순위 요건이다.** 도구를 못 부르면 2.5억 행이 통째로 무용지물이 되고,
남는 것은 데이터를 모르는 채팅봇뿐이다. 한국어 품질이 아무리 나아도 교체할 수 없다.

### 벤치마크 도구

`tools/bigdata/model_bench.py` — 인상이 아니라 측정으로 판단하기 위해 만들었다.
이 제품에서 실제로 중요한 순서대로 잰다:

1. **도구 호출 정확도** — 도구를 못 부르면 나머지는 의미가 없다
2. **언어 순수성** — 한국어 답변에 한자(중국어)·가나(일본어)가 섞이는 비율
3. **지시 준수** — "숫자만", "한 문장" 같은 제약
4. **속도** — tok/s

각 항목을 여러 번 반복한다. LLM은 같은 프롬프트에도 다르게 답하므로
1회 측정으로 모델을 비교하는 것은 운을 재는 것이다.

```bash
/Volumes/T7/bigdata/env/bin/python tools/bigdata/model_bench.py \
  qwen2.5:7b-instruct exaone3.5:7.8b --repeats 3
```

측정된 것: **qwen2.5 도구 호출 8/8 (100%), 인자까지 정확 8/8 (100%)**.
도구 호출만큼은 신뢰할 수 있다.

### 벤치마크를 만들며 고친 것

처음에는 도구 요청을 던져 보고 실패로 판단했다. 그러면 로그에
`HTTP Error 400: Bad Request` 만 8번 찍히고, 그것이 **모델이 도구를 못 부르는 것인지
내 요청이 틀린 것인지 구분되지 않는다.**
→ `/api/show` 로 능력을 먼저 확인하고, 미지원이면 명시적으로 표시한 뒤 측정을 건너뛴다.

### 다음에 볼 후보

도구 호출을 지원하면서 한국어가 나은 모델이 필요하다. Ollama에서
`capabilities` 에 `tools` 가 있는지 먼저 확인하면 헛수고를 줄일 수 있다:

```bash
curl -s http://127.0.0.1:11434/api/show -d '{"model":"<모델>"}' | jq .capabilities
```

후보: `qwen3` 계열(도구 지원, qwen2.5보다 다국어 개선), `llama3.3`(도구 지원, 한국어는 약함).
현실적으로는 **로컬 7B급에서 한국어와 도구 호출을 동시에 잘하는 모델이 아직 드물다** —
프런티어 모델을 쓸 수 있게 되면 그쪽이 여전히 크게 낫다.

## 15. 운영 중 발견한 결함 — 재빌드가 임베딩을 조용히 지웠다

`sido_norm` 을 넣느라 DB를 재빌드한 뒤, **의미 검색이 죽어 있었다.**

`build.py db` 는 DuckDB 파일을 통째로 새로 만든다. `catalog_embeddings` 는 `embed` 단계에서
그 파일 **안에** 만들어지므로 함께 사라진다.

나쁜 것은 사라졌다는 사실이 아니라 **조용하다는 것**이다. 도구는 임베딩이 없으면
부분일치 검색으로 내려가도록 설계돼 있어(없는 배포에서도 동작해야 하므로),
"집값" 같은 질의가 그냥 결과 없음이 될 뿐 에러가 나지 않는다.
하마터면 그 상태로 "완료"라고 보고할 뻔했다.

고친 것:
- `db` 종료 시 **"임베딩 테이블이 초기화됐다"고 경고**를 출력한다
- `rebuild` 명령을 추가했다 (db + embed를 항상 함께)

### 이 실수가 드러낸 더 중요한 것

`s4:bigdata` 검증에는 원래부터 **"'집값' → 주택가격 매칭"** 테스트가 있었다.
재빌드 직후에 검증만 돌렸으면 즉시 잡혔을 문제다.
**데이터를 다시 만든 뒤 검증을 건너뛴 것이 진짜 실수였다.**

복구 후 재검증: `Sprint#4 PASS 38/38`, 임베딩 6,597/6,597.

### 15시간짜리 좀비 대기 루프

작업 관리 패널에 "실행 중"으로 7개가 15시간째 떠 있었다. 실제 작업이 아니라
완료를 감시하려고 띄운 `until ... sleep` 루프였다.

종료 조건을 로그 파일 내용으로 잡아두고(`grep -c 'tok/s' == 2`),
벤치마크를 여러 번 재시작하며 **그 로그를 매번 덮어썼다.** `chain.log` 는 아예 지웠다.
이미 지나간 조건을 영원히 기다리는 상태가 됐다.

교훈: 대기 루프의 종료 조건을 **자신이 지우거나 덮어쓸 파일**에 걸면 안 된다.
프로세스 존재 여부로 거는 것이 나은데, 그때는 `pgrep -f` 가
**자기 자신의 명령줄을 매칭한다**는 함정이 있다 (이것도 실제로 겪었다).

### 파이프라인 차단 해소

다른 세션이 추가한 `local-auth.test.ts` 의 lint 오류 7건이 `eslint .` 전체를 막고 있었다.

## 16. 모델 교체 — qwen3:8b 로 전환

§14에서 "qwen2.5 유지"라고 결론냈다. **그 결론은 틀렸다.** 후보를 늘리고 계측기를 고치자
결과가 완전히 뒤집혔다.

### 최종 실측

| 모델 | 도구 | 인자 | 한국어 | 지시 | tok/s |
|---|---:|---:|---:|---:|---:|
| **qwen3:8b** | **100%** | **100%** | **100%** | **100%** | 5.8 |
| qwen2.5:7b-instruct | 100% | 100% | 62% | 100% | 5.8 |
| llama3.1:8b | 88% | 75% | 88% | 100% | 7.2 |
| exaone3.5:7.8b | 미지원 | — | 100% | 100% | 5.7 |

qwen3:8b 가 전 항목 만점이다. 속도도 qwen2.5 와 같다.

### 하마터면 멀쩡한 모델을 탈락시킬 뻔했다

1차 측정에서 qwen3 는 **도구 38% / 한국어 0%** 로 최하위였다.
이상해서 파고드니 모델이 아니라 **내 계측기의 결함**이었다:

```
max_tokens=120 → content 0자,   reasoning 639자,  finish=length
max_tokens=800 → content 469자, reasoning 1858자, finish=stop
```

`max_tokens` 는 '사고 + 응답'을 함께 제한한다. qwen3 는 사고 모델이라
예산을 사고가 다 먹고 **가시 응답이 0자**가 됐다. 그것이 "한국어를 못 한다"로 집계됐다.

**이 저장소는 같은 버그를 이미 한 번 겪었다.** Sprint #1 에서 claude-opus-5 가 똑같이
빈 응답을 냈고, 그래서 라우터에 `THINKING_HEADROOM = 4096` 을 넣었다.
**교훈을 제품에는 적용했으면서 계측기에는 적용하지 않았다.**

고친 것:
- `capabilities` 에 `thinking` 이 있으면 출력 예산을 **+700 토큰** 자동 부여
- **빈 응답을 언어 실패와 구분해서 집계** — 이전에는 빈 응답이 "한국어 아님"에 섞여
  원인이 가려졌다. 이제 "빈 응답 N건 — 사고 예산 부족일 수 있다"고 따로 경고한다

### 제품 쪽 조치

로컬 모델 카탈로그가 사고 모델을 인식하지 못하면 **실서비스에서도 같은 빈 응답**이 난다.
모델 id 로 추정해 `thinksByDefault` 를 세우고, 회귀 테스트로 고정했다
(`packages/ai/src/__tests__/local-thinking.test.ts`, 5개).

```ts
/(^|[/:._-])(qwen3|deepseek-r1|qwq|magistral|reasoning|thinking)/i
```

`qwen2.5` 가 `qwen3` 패턴에 걸리지 않는지도 테스트에 넣었다 — 접두사만 겹쳐 오탐하면
불필요한 예산이 낭비된다.

기본값도 `LOCAL_LLM_MODELS=qwen3:8b` 로 바꿨다.

### 실서비스 확인

## 검증 하네스도 오프라인이어야 한다

제품은 외부 키 없이 도는데 **검증만 클라우드 키를 요구하고 있었다.** 전체 파이프라인을
돌려 보니 4개 단계가 실패했고, 하나도 제품 결함이 아니었다 —
전부 "검증 도구가 오프라인 구성을 모른다"였다.

| 단계 | 증상 | 실제 원인 |
|---|---|---|
| Memory stress | `no_providers` 로 크래시 | 하네스가 `LocalAdapter` 를 등록하지 않았다 |
| Security | `sec.prompt_injection: no provider key` | `ANTHROPIC_API_KEY` 만 보는 게이트 |
| Performance | `perf.llm_concurrency: no provider key` | 같은 게이트 |
| Performance | `expected 1024 dimensions, not 1536` | `hashEmbedder()` 기본 차원이 상수 |

### 1) 조립부가 아는 프로바이더는 하네스도 알아야 한다

`apps/api/src/context.ts` 는 `LOCAL_LLM_BASE_URL` 이 있으면 `LocalAdapter` 를 등록한다.
하네스는 그러지 않았다. 하네스 파일 첫머리에 적힌 설계 원칙
("테스트 전용 배선을 피한다")의 정확한 위반이다 — 다만 방향이 반대였다.
하네스가 통과했는데 서버가 실패하는 게 아니라, **서버는 도는데 하네스만 죽었다.**

로컬 모델은 `MODEL_CATALOG`(코드 상수)에 없으므로 카탈로그 합류도 함께 해야 한다.
어댑터만 등록하면 후보 모델이 0개가 되어 똑같이 `no_providers` 로 죽는다.

### 2) 프로바이더 게이트를 특정 키에 묶지 않는다

두 시험 모두 `h.router` 경유라 프로바이더에 무관한데 `ANTHROPIC_API_KEY` 만 봤다.
게다가 건너뛸 때 `check(..., false, ...)` 로 **실패로 기록**했다 —
"방어가 깨졌다"와 "검증을 못 돌렸다"가 구분되지 않았다.

### 3) 임베딩 차원을 상수로 두지 않는다

`hashEmbedder(dim = 1536)` 은 OpenAI 전제였다. DB가 bge-m3(1024)로 옮겨간 뒤에도
1536을 만들어 insert 단계에서 터졌다. 이제 하네스가 **DB pg_attribute 에서 실제 차원을
읽어** 내려보내고, 실제 임베더를 쓸 때는 부팅 시점에 한 번 재서 어긋나면 즉시 실패한다.

```
임베딩 차원 불일치: 임베더 1536 vs DB 컬럼 1024.
EMBED_DIM=1024 node scripts/set-embedding-dim.mjs 로 스키마를 맞춰라.
```

### 4) 성능 게이트가 임베더 처리량을 재고 있었다

`perf.ltm_recall` 은 `p95 < 500ms` 를 걸고 있었는데 881ms 로 실패했다.
구간을 갈라 재니 원인이 분명했다:

```
임베딩(로컬 bge-m3, CPU 단건)   62ms
pgvector 검색                    2ms
```

동시성 25면 Ollama 가 직렬화돼 임베딩만 943ms(p95)가 된다. 우리 코드는 그대로인데
임베더를 OpenAI에서 로컬로 바꿨다는 이유만으로 성능이 '회귀'한 것처럼 보인다.

그래서 `recall()` 을 `recallByVector()` 로 쪼개, **우리가 책임지는 구간에만 게이트를 걸고**
임베더는 환경 특성으로 따로 계측해 출력한다. 숨기지 않되 합치지도 않는다.

```
embed x32 (c=25, 환경 특성)          p50=709ms p95=943ms
ltm.recall x1000 (c=25, 임베딩 제외)  p50= 28ms p95= 82ms  438 rps
PASS  perf.ltm_recall — 500 벡터, 질의 임베딩 제외
```

### 오프라인 실측 성능 (MacBook Air, qwen3:8b Q4_K_M)

`phase6` 를 로컬 모델로 완주시킨 실제 수치다 (12 스트림, 동시성 6):

```
TTFT   p50=269s  p95=582s      ← 동시성 6에서 Ollama 가 요청을 직렬화한다
TPS    p50=31.1 tok/s          ← 첫 토큰 이후 생성 속도
비용   $0.00000 (302 in / 4887 out)
```

TTFT 가 269초인 것은 6개를 동시에 던졌기 때문이다. 순차 처리 시 생성 속도 자체는
31 tok/s 로 충분하다. **로컬 추론은 1인 사용에는 실용적이지만 동시 사용자에게는 아니다** —
이것이 GPU 서버 없이 자체 호스팅할 때의 실제 제약이다.

전체 결과: **PHASE 6 — Performance & load: PASS (16/16)**, 소요 13분.

### 5) SKIP 은 통과가 아니다 — 라우터 검증이 통째로 건너뛰어지고 있었다

전체 파이프라인 출력에 이 한 줄이 있었다:

```
SKIP  Router — no provider key configured
```

`verify-all.mjs` 의 `hasKey` 가 클라우드 키 4개만 봤기 때문이다. 로컬 추론 서버도
프로바이더인데 세지 않았다. 결과적으로 **AI 라우터 전체가 미검증 상태**로
"16 passed" 안에 조용히 섞여 있었다.

`LOCAL_LLM_BASE_URL` 을 `hasKey` 에 포함시키고 phase3 자체도 고쳤다:

- **랭킹 정책은 순수 계산이다.** 어떤 프로바이더도 호출하지 않는데, 실제 어댑터 유무로
  후보 카탈로그가 걸러지는 바람에 키 없는 환경에서는 정책이 검증되지 않았다.
  스트림하지 않는 스텁을 모든 프로바이더에 꽂아 **항상** 재도록 했다.
- **폴백 시험의 순위를 우연에 맡기지 않는다.** 고장난 프로바이더가 1순위여야 폴백을
  시험하는 것이 되는데, 2순위가 무료 로컬 모델이 되자 cheap 가중에서 로컬이 1위로 올라가
  고장난 쪽을 아예 거치지 않았다 — 그래도 "폴백 성공"으로 보였다. 카탈로그로 고정했다.
- **브레이커 판정을 모델 속도가 좌우하지 않게 한다.** 서킷브레이커는 5회 실패로 열리고
  60초 뒤 half-open 으로 스스로 리셋된다(정상 동작). 그런데 회복 담당이 로컬 7B 라
  6회 반복에 60초가 넘어, 스냅샷을 볼 때쯤 이미 리셋돼 `open=false` 로 읽혔다.
  실패 누적 구간만 즉답 스텁으로 바꿔 밀리초 단위로 만들었다.
  (실제 프로바이더를 통한 폴백은 바로 앞 두 단언이 증명한다.)

결과:


`policy.cost_cap` 에 `qwen3:8b` 가 $0 후보로 잡히는 것이 로컬 모델이 카탈로그에 실제로
합류했다는 증거다.

## 정당한 요청이 "줄을 섰다"는 이유로 죽고 있었다 — `UND_ERR_HEADERS_TIMEOUT`

성능 검증에서 12개 스트림 중 1~2개가 실패했다. 처음에는 그냥 `err=1` 만 보였다.

```
FAILED: perf.llm_concurrency — p50=338071ms p95=654453ms, no failures at c=6, n=11/12 err=1
```

**왜 실패했는지 알 방법이 없었다.** `load()` 는 마지막 오류를 보관하는데(그러라고 주석까지
달아 두고) 정작 단언 메시지에 찍지 않았다. 먼저 그걸 고쳤다:

```
n=10/12 err=2 lastError="[local] network failure: fetch failed (UND_ERR_HEADERS_TIMEOUT)"
TTFT p50=343109ms
```

### 원인

Node 내장 fetch(undici)의 **기본 헤더 타임아웃은 300초**다. 로컬 추론 서버는 용량을 넘는
요청을 받아 두고 순서를 기다리게 하는데, 그동안 응답 헤더를 보내지 않는다.
동시성 6에서 TTFT p50 이 343초 — 300초를 넘는 요청이 네트워크 오류로 죽는다.

**서버는 멀쩡하고 우리 요청도 정당한데, 줄을 서 있었다는 이유만으로 실패한다.**
검증 환경만의 문제가 아니다. 오프라인 구성에서 사용자 몇 명이 동시에 채팅하면 그대로 재현된다.

### 고침 — 대기를 서버 큐에서 우리 큐로 옮긴다

`LocalAdapter.stream` 에 FIFO 세마포어(기본 2)를 걸었다.
우리 프로세스에서 기다리는 시간은 HTTP 타임아웃 대상이 아니다.
슬롯이 났을 때 비로소 연결을 열므로 헤더가 곧바로 온다.

**전체 소요 시간은 같다 — 바뀌는 것은 죽느냐 기다리느냐다.**

임베딩 게이트와 **분리**했다. 카운터를 공유하면 임베딩 폭주가 채팅을 굶기고, 그 반대도
마찬가지다. 둘은 자원을 나눠 쓰지만 서로의 대기열이 되어서는 안 된다.

```
LOCAL_CHAT_CONCURRENCY   기본 2   (이 머신의 7B 는 사실상 한 번에 하나를 생성한다)
LOCAL_EMBED_CONCURRENCY  기본 4
```

수정 후 `PHASE 6 — Performance & load: PASS`.

### 단위 테스트가 지키는 것

| 테스트 | 왜 |
|---|---|
| 상한 준수 | 상한이 사라지면 같은 장애가 재발한다 |
| **소비자가 도중에 멈춰도 슬롯 반납** | 새면 취소 몇 번에 게이트가 영구히 막힌다 — 사용자에게는 "앱이 멈췄다" |
| 두 게이트가 서로를 굶기지 않음 | 분리한 이유 자체를 고정한다 |
| 임베딩 상한·FIFO·오류 시 반납 | 앞서 만든 게이트의 계약 |

특히 두 번째가 중요하다. 스트림 소비자가 `break` 하면 제너레이터가 `return()` 으로 끝나는데,
`finally` 로 반납하지 않으면 그때 슬롯이 샌다. 기능 테스트로는 절대 드러나지 않는다.

### 교훈

이 결함은 **실패 메시지가 원인을 말하지 않아** 두 번의 전체 실행 동안 "가끔 나는 flake" 로
지나갔다. `lastError` 를 메시지에 넣는 세 줄이 없었다면 지금도 몰랐을 것이다.
검증이 실패를 보고할 때는 **무엇이 틀렸는지가 아니라 왜 틀렸는지**를 말해야 한다.

## 로컬 7B 의 에이전트 신뢰도 — 관측된 그대로 적는다

`s2:scenario`(전체 제품 시나리오: 생성 → 결함 주입 → 에이전트 수리 → 커밋 → 기억 → 플러그인)를
로컬 qwen3:8b 로 돌린 결과는 **3회 중 2회 통과**다.

실패한 1회의 형태:

```
FAILED: s4.agent_edited — write_file called 0 time(s)
```

앞 단계에서 같은 모델이 `write_file` 을 정상 호출해 파일을 만들었다(`s2.file_written` 통과).
즉 **능력 부재가 아니라 비결정성**이다. 수리 단계에서 도구를 부르지 않고 말로만 답했다.

### 원인을 단정하지 않는다

같은 시점에 `UND_ERR_HEADERS_TIMEOUT` 문제를 고쳤지만, **그것이 이 실패의 원인이라고
말할 수 없다.** 이 시나리오의 에이전트 루프는 한 번에 하나씩 순차로 요청하므로
동시성 게이트가 개입할 자리가 없다. 통과한 재실행은 증거이지 인과가 아니다.

### 대신 다음 실패를 진단 가능하게 만들었다

실패 메시지가 "0번 불렀다"뿐이면 **모델이 무엇을 했는지**가 빠진다.
재현 말고는 방법이 없어진다 — 그런데 이건 재현되지 않는 종류의 실패다.

```ts
`write_file called 0 time(s) — ${fix.turns}턴, 도구 [${...}], 모델의 마지막 응답: "${...}"`
```

턴 수, 실제로 부른 도구 목록, 모델의 마지막 발화를 남긴다.
다음에 같은 일이 생기면 그 한 줄로 판단할 수 있다 —
사고 토큰에 예산이 소진됐는지, 도구 스키마를 오해했는지, 그냥 설명만 하고 끝냈는지.

### 실무적 함의

**오프라인 구성에서 에이전트 작업은 재시도를 전제로 설계해야 한다.**
7B 모델은 도구 호출을 대체로 하지만 항상 하지는 않는다.
7.4절(프롬프트 주입 방어)과 6.6절(생성 속도)이 보여주듯 능력 자체는 충분하다 —
문제는 **일관성**이고, 그것은 모델 크기의 함수다. 이 제약을 모르고 무인 파이프라인에
로컬 7B 를 넣으면 조용히 실패하는 작업이 생긴다.

## 개발 환경 복구가 매번 수작업이었다 — `scripts/dev-up.sh`

기기를 바꾸자 로컬 환경이 통째로 사라졌다. 복구해 보니 단계가 이랬다:

1. colima / Docker 스택 기동
2. **Ollama 를 T7 모델 경로로** 기동 (`OLLAMA_MODELS` 없이 띄우면 19GB 를 맥에 새로 받는다)
3. 설정 파일 재작성 (`/tmp` 에 두었던 것이 사라졌다)
4. **API 키 재발급** — 이건 복구가 아니라 재발급이다. DB 에는 sha256 해시만 있어서
   평문은 발급 시점에만 존재한다. 잃으면 되찾을 방법이 없다.
5. API 서버 기동

10단계 가까이 되고, 그중 하나는 원복이 불가능하다. 한 번에 되게 만들었다.

```
$ scripts/dev-up.sh
▸ postgres/redis 기동
  postgres: healthy
▸ ollama 기동 (모델: /Volumes/T7/bigdata/ollama-models)
  ollama: 모델 5개
  키: /Volumes/T7/bigdata/secrets/aios-dev-key.txt
▸ API 서버 기동
  api: http://127.0.0.1:8790
export AIOS_BASE_URL=http://127.0.0.1:8790
export AIOS_API_KEY=aios_live_...
```

**콜드 스타트 10초.** 이미 떠 있으면 아무것도 다시 하지 않는다(멱등).
전부 내린 상태와 이미 떠 있는 상태 양쪽에서 실행해 확인했다.

### 스크립트가 강제하는 것

- **T7 마운트 확인 후에만 진행한다.** 마운트 없이 돌면 모델과 데이터가 맥 내장 디스크에
  새로 만들어져 저장 제약을 조용히 어긴다. 그래서 없으면 즉시 멈춘다.
- **모델 0개는 기동 성공이 아니다.** Ollama 는 잘못된 경로로도 멀쩡히 뜨고 빈 목록을 준다.
  실제로 그렇게 떠 있었고, 모델이 사라진 줄 알았다. 개수를 확인해 0이면 실패로 처리한다.
- 설정은 `/tmp` 가 아니라 저장소 안 `.env.local`(gitignore 됨), 키는 저장소 **밖**
  `/Volumes/T7/bigdata/secrets/`(0600). 키를 저장소에 두지 않는 이유는 명백하다.

## 상한을 아무리 잘 잡아도 못 고치는 것 — 헤더 타임아웃 자체를 껐다

동시성 상한은 대기를 **줄이지만 없애지 못한다.**
더 큰 모델(70B CPU)이나 부하가 걸린 기기에서는 **동시성 1에서도** 첫 토큰이 300초를 넘는다.
그러면 그 모델은 상한을 어떻게 잡아도 아예 쓸 수 없다.

원인은 우리 코드가 아니라 클라이언트 기본값이다:
**Node 내장 fetch 는 undici 기본값을 쓰고 헤더 타임아웃 300초가 고정이며 설정할 방법이 없다.**

### 왜 npm undici 를 쓰는가

내장 fetch 에 npm undici 의 `Agent` 를 넘기면 **거부한다**:

```
내장 fetch + npm undici Agent  → UND_ERR_INVALID_ARG ("fetch failed")
undici 자체 fetch + 같은 Agent → 200 OK
```

두 undici 인스턴스는 호환되지 않으므로 한쪽으로 통일해야 한다.
그래서 `OpenAiAdapter` 에 `fetchImpl` 이음매를 두고 **로컬 어댑터만** 갈아끼운다.

```ts
const localDispatcher = new Agent({
  headersTimeout: 0,      // 첫 응답까지 무제한 — 로컬 추론에서 대기는 정상이다
  bodyTimeout: 0,         // 토큰 사이 간격도 제한하지 않는다
  connectTimeout: 10_000, // 다만 '서버가 없음'은 빨리 알아야 한다
});
```

**클라우드 어댑터는 내장 fetch 를 그대로 쓴다.** 거기서는 300초 상한이 올바른 방어다 —
외부 프로바이더가 5분간 헤더도 못 보내면 그건 진짜 장애이고, 빨리 다음 후보로 넘어가야 한다.
같은 규칙을 모든 프로바이더에 적용하는 것이 오히려 틀렸다.

실제 취소는 호출자의 `AbortSignal` 이 담당한다 — 요청마다 다르므로 그게 옳은 자리다.

### 300초를 기다리지 않고 증명하는 법

헤더를 일부러 3초 늦게 보내는 서버를 세우고, 타임아웃이 걸린 경우와 끈 경우를 비교한다.

| 시험 | 결과 |
|---|---|
| 같은 지연 + 짧은 헤더 타임아웃 | `UND_ERR_HEADERS_TIMEOUT` 으로 죽는다 — **우리가 겪은 장애** |
| 같은 지연 + `LocalAdapter` | 기다렸다가 성공한다 |
| 응답 없는 주소 | 11초 안에 실패한다 — 무제한 대기가 아니다 |

세 번째가 중요하다. 타임아웃을 껐다고 죽은 주소에 영원히 매달리면 그건 다른 종류의 장애다.
`connectTimeout` 이 그 경우를 잡는다.

처음 쓴 시험은 400ms 지연 / 100ms 타임아웃이었는데 **발동하지 않았다** —
undici 의 헤더 타임아웃은 공용 타이머로 검사해 해상도가 수백 ms 단위다.
간격을 실제로 발동하는 크기(3초 / 500ms)로 벌려야 시험이 성립한다.

### 상한은 남긴다 — 역할이 바뀌었을 뿐

기본 `LOCAL_CHAT_CONCURRENCY=2` 는 그대로다. 이제 그것은 **충돌 방지 장치가 아니라
지연·처리량 조절 손잡이**다. 더 느린 기기(Air)에서도 안전한 값을 기본으로 두고,
빠른 기기는 위 실측표를 보고 올리면 된다. 상한을 올려도 이제는 죽지 않는다 — 느려질 뿐이다.
